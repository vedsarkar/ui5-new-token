# Writing Storybook Stories

This guide explains how to write effective Storybook stories that serve as automated test cases for visual, interaction, and accessibility testing. It covers the CSF Next format, testing integration with Chromatic, and the separation between stories and documentation.

> **🎯 Key Principle:** A story is a test case, not documentation. Each story should define a single, testable component state.

### Basic Structure

```tsx
import { fn } from "storybook/test";
import preview from "@/.storybook/preview";
import { Button } from "./Button";
import cssClasses from "./Button.module.css";

const meta = preview.meta({
  component: Button,
  parameters: {
    layout: "centered",
    cssClasses,
  },
  args: {
    onClick: fn(),
  },
});

export const Default = meta.story({
  args: {
    children: "Button",
  },
});

export const Primary = meta.story({
  args: {
    variant: "filled",
    color: "primary",
    children: "Primary Button",
  },
});
```

### Writing Testable Stories

Every story should capture a **single, deterministic component state**:

**✅ Do:** One state per story

```tsx
export const Disabled = meta.story({
  args: {
    disabled: true,
    children: "Disabled Button",
  },
});

export const DisabledPrimary = meta.story({
  args: {
    variant: "filled",
    color: "primary",
    disabled: true,
    children: "Disabled Primary",
  },
});
```

**❌ Don't:** Multiple states or complex logic in stories

```tsx
// Bad: This is not a testable story
export const AllStates = meta.story({
  render: () => (
    <div>
      <Button>Default</Button>
      <Button disabled>Disabled</Button>
      <Button variant="primary">Primary</Button>
    </div>
  ),
});
```

## Stories vs. Documentation

Stories and documentation serve different purposes and must be kept separate.

### Stories: Define Component States

A story file (`.stories.tsx`) should contain **only** component state definitions:

- Props combinations (`args`)
- Layout configuration (`parameters.layout`)
- Action handlers (`fn()`)

**✅ Do:** Clean, focused stories

```tsx
export const Small = meta.story({
  args: {
    size: "small",
    children: "Small Button",
  },
});

export const Medium = meta.story({
  args: {
    size: "medium",
    children: "Medium Button",
  },
});

export const Large = meta.story({
  args: {
    size: "large",
    children: "Large Button",
  },
});
```

**❌ Don't:** Documentation or explanations in story files

```tsx
// Bad: Story file contains documentation
const componentDescription =
  "TreeList renders hierarchical data with expand/collapse controls...";

const cssVariables = [
  { name: "--reltio-tree-list-font-family", description: "Font family..." },
  // ...20 more lines of documentation
];

export const WithCustomCssVariables = meta.story({
  render: ({ style, ...args }) => (
    <div>
      {/* Rendering documentation alongside the component */}
      <div style={{ background: "#0f172a", padding: "10px" }}>
        <div>CSS variables</div>
        <ul>
          {cssVariables.map((v) => (
            <li key={v.name}>{v.name}: {v.description}</li>
          ))}
        </ul>
      </div>
      <TreeList {...args} />
    </div>
  ),
});
```

### Documentation: Use Autodocs

Component documentation belongs in [Autodocs](https://storybook.js.org/docs/writing-docs/autodocs) or MDX files — not in stories.

Autodocs automatically generates documentation from:

- Component prop types (via TypeScript or PropTypes)
- JSDoc comments in component source
- Story metadata and args

> **💡 Note:** Autodocs is enabled globally in `.storybook/preview.tsx`, so all components get documentation pages automatically.

For custom documentation, create a separate MDX file:

```
components/
  Button/
    Button.tsx           # Component implementation
    Button.stories.tsx   # Stories (test cases only)
    Button.mdx           # Custom documentation (optional)
```

## Testing Actions with fn()

Use the [`fn()` function](https://storybook.js.org/docs/essentials/actions) from `storybook/test` to spy on callback props.

### Basic Usage

```tsx
import { fn } from "storybook/test";

const meta = preview.meta({
  component: Button,
  args: {
    onClick: fn(),
  },
});
```

### Why fn() Instead of Action Matching

<table>
  <thead>
    <tr>
      <th>Approach</th>
      <th>Pros</th>
      <th>Cons</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><code>fn()</code> (recommended)</td>
      <td>Type-safe, testable in play functions, explicit</td>
      <td>Requires manual assignment</td>
    </tr>
    <tr>
      <td><code>argTypesRegex</code> (legacy)</td>
      <td>Automatic matching</td>
      <td>Not type-safe, not available in play functions</td>
    </tr>
  </tbody>
</table>

### Testing Interactions

When using `fn()`, you can assert on calls in play functions:

```tsx
import { fn } from "storybook/test";
import { expect, userEvent, within } from "storybook/test";

export const ClickTest = meta.story({
  args: {
    onClick: fn(),
    children: "Click me",
  },
  play: async ({ args, canvasElement }) => {
    const canvas = within(canvasElement);
    const button = canvas.getByRole("button");

    await userEvent.click(button);

    await expect(args.onClick).toHaveBeenCalledTimes(1);
  },
});
```

### No Custom Logging

Storybook's [Actions panel](https://storybook.js.org/docs/essentials/actions) automatically displays all `fn()` calls with their arguments. Never use `console.log()`, DOM manipulation, or custom UI to display callback data.

**✅ Do:** Let fn() handle logging automatically

```tsx
const meta = preview.meta({
  component: TreeList,
  args: {
    onExpand: fn(),  // Calls appear in Actions panel with all arguments
  },
});

export const ControlledExpanded = meta.story({
  args: {
    expandedKeys: ["root", "node-1"],
  },
});
```

**❌ Don't:** Create custom logging UI or use console.log

```tsx
// Bad: Manual DOM manipulation for logging
export const ControlledExpanded = meta.story({
  args: {
    onExpand: (keys, node) => {
      // Bad: Custom logging via DOM
      document.getElementById("expanded-keys").innerHTML = JSON.stringify(keys);
      document.getElementById("toggled-node").innerHTML = JSON.stringify(node);
    },
  },
  render: (args) => (
    <>
      {/* Bad: Custom debug UI */}
      <div style={{ fontFamily: "monospace", background: "#f7f7f7" }}>
        <div><strong>Expanded keys:</strong> <span id="expanded-keys"></span></div>
        <div><strong>Toggled node:</strong> <span id="toggled-node"></span></div>
      </div>
      <TreeList {...args} />
    </>
  ),
});
```

> **💡 Tip:** The Actions panel shows the full call history with expandable argument inspection. This is more powerful than any custom logging solution.

## ArgTypes Mapping for Complex Props

When a component prop accepts complex values (JSX elements, objects, functions), use the built-in [argTypes mapping](https://storybook.js.org/docs/api/arg-types#mapping) instead of creating custom args with render functions.

### Why Use Mapping?

<table>
  <thead>
    <tr>
      <th>Approach</th>
      <th>Pros</th>
      <th>Cons</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><code>argTypes.mapping</code> (recommended)</td>
      <td>Declarative, URL-shareable, works with controls, testable</td>
      <td>Only predefined values available</td>
    </tr>
    <tr>
      <td>Custom arg + render function</td>
      <td>Full control over rendering</td>
      <td>Breaks testing, complex logic in stories</td>
    </tr>
  </tbody>
</table>

### How Mapping Works

The `mapping` property creates a lookup table connecting simple string options to complex values:

**✅ Do:** Use argTypes mapping for complex props

```tsx
import { CustomLabel, TagLabel, InfoLabel } from "./labels";

const meta = preview.meta({
  component: TreeList,
  argTypes: {
    LabelComponent: {
      control: { type: "select" },
      options: ["default", "tag", "info"],
      mapping: {
        default: CustomLabel,
        tag: TagLabel,
        info: InfoLabel,
      },
    },
  },
});

export const WithTagLabel = meta.story({
  args: {
    LabelComponent: "tag", // Maps to TagLabel component
  },
});
```

**❌ Don't:** Create custom args with render function logic

```tsx
// Bad: Custom arg requires complex render function
type CustomLabelArgs = ComponentProps<typeof TreeList> & {
  labelVariant: "default" | "tag" | "info";
};

export const CustomLabel = meta.story({
  argTypes: {
    labelVariant: {
      control: { type: "inline-radio" },
      options: ["default", "tag", "info"],
    },
  },
  args: {
    labelVariant: "tag",
  },
  render: (rawArgs) => {
    const { labelVariant, ...treeListArgs } = rawArgs;

    // Bad: Manual mapping logic inside render
    const LabelMap = {
      default: DefaultLabel,
      tag: TagLabel,
      info: InfoLabel,
    };
    const Label = LabelMap[labelVariant];

    return <TreeList {...treeListArgs} LabelComponent={Label} />;
  },
});
```

## Free-Form Props vs. Enum Variants

Not every prop needs multiple stories. The rule depends on whether the prop has **fixed variants** or accepts **arbitrary values**.

**Enum-like props** (`variant`, `color`, `size` with predefined options like `"small" | "medium" | "large"`) — create a story for each value. Each produces a visually distinct state that Chromatic should snapshot-test independently.

**Free-form props** (`size` as arbitrary CSS string, `width`, `maxHeight`, `label`, `placeholder`, etc.) — create **one** story demonstrating usage. Developers can see the pattern in the source code and apply any value they need. Creating `Small`, `Medium`, and `Large` stories for a prop that accepts `"20px"`, `"2rem"`, or `"100%"` adds noise without testing value.

**✅ Do:** One story for a free-form size prop

```tsx
export const CustomSize = meta.story({
  args: {
    size: "64px",
  },
});
```

**❌ Don't:** Multiple stories for different arbitrary values of the same prop

```tsx
export const Small = meta.story({
  args: { size: "20px" },
});

export const Medium = meta.story({
  args: { size: "32px" },
});

export const Large = meta.story({
  args: { size: "64px" },
});
```

> **Rule of thumb:** If the prop value is a union of specific keywords — one story per keyword. If the prop accepts any string/number — one story is enough.

## Best Practices

### Story Structure

1. **One state per story** — each export tests a specific prop combination
2. **Minimal args** — only include props relevant to the state being tested
3. **Descriptive names** — story names should describe what state is being tested
4. **No documentation** — keep explanatory content in MDX or autodocs
5. **One story per free-form prop** — don't create multiple stories for different values of the same arbitrary-value prop

### Testing Focus

1. **Cover all variants** — create stories for each visual variant (enum-like props)
2. **Cover all states** — disabled, loading, error, empty, etc.
3. **Cover edge cases** — long text, missing data, boundary conditions
4. **Use fn() for callbacks** — enables action logging and interaction testing
5. **Demonstrate free-form props once** — one story to show the prop works, not multiple value permutations

### What NOT to Include

1. **Inline documentation** — use autodocs or MDX instead
2. **Multiple components per story** — unless testing composition
3. **Complex render functions** — keep stories declarative
4. **Wrapper components** — use decorators for consistent wrappers
5. **Redundant value permutations** — multiple stories varying only a free-form prop value

## Quick Reference

### Minimal Story File Template

```tsx
import { fn } from "storybook/test";
import preview from "@/.storybook/preview";
import { MyComponent } from "./MyComponent";
import cssClasses from "./MyComponent.module.css";

const meta = preview.meta({
  component: MyComponent,
  parameters: {
    layout: "centered", // or "padded", "fullscreen"
    cssClasses,
  },
  args: {
    onChange: fn(),
    onClick: fn(),
  },
});

export const Default = meta.story({
  args: {
    // minimal props
  },
});

export const VariantA = meta.story({
  args: {
    variant: "a",
  },
});

export const Disabled = meta.story({
  args: {
    disabled: true,
  },
});
```

### CSS Classes Parameter

Every component with a CSS Module must expose its class map via `parameters.cssClasses`. This powers the **CSS Classes** table on each component's docs page, making stable selectors discoverable.

```tsx
import cssClasses from "./MyComponent.module.css";

const meta = preview.meta({
  component: MyComponent,
  parameters: {
    cssClasses,
  },
});
```

The CSS module import returns the class name mapping (e.g. `{ root: "MyComponent_root__x1y2z", ... }`). The docs page uses this to display the stable selectors (e.g. `.reltio_MyComponent_root`) that consumers can target for [external customization](/?path=/docs/guides-component-customization--docs).

### Checklist

- [ ] Uses CSF Next format (`preview.meta()` and `meta.story()`)
- [ ] Each story defines a single component state
- [ ] No documentation or explanatory text in stories
- [ ] All callback props use `fn()` from `storybook/test`
- [ ] Complex props use `argTypes.mapping` instead of custom render logic
- [ ] Story names are descriptive and follow naming conventions
- [ ] All visual variants (enum-like props) have corresponding stories
- [ ] All interactive states (disabled, loading, etc.) have stories
- [ ] Free-form props have one demonstrative story each, not multiple value permutations
