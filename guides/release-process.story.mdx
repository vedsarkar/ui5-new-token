# Release Process

This guide explains **how a code change in `reltio-design-platform` reaches the npm registry** as a new version of `@reltio/design`. It is the canonical reference for reviewers, maintainers, and consumers who want to understand when a release will happen and what each release contains.

> **🎯 Key Principle:** Every PR carries its own release intent — a Changesets file describing the user-visible impact. Releases are deliberate, human-reviewed aggregations of those intents: the human review happens on the auto-generated **version PR**, not on the publish itself. Merging a feature PR to `main` never publishes anything; only merging a version PR does, and the publish that follows is fully automated.

> **For contributors authoring changesets**, the step-by-step task workflow (CLI prompts, bump-type rubric, summary examples, when to use `--empty`) lives in [`CONTRIBUTING.md`](https://bitbucket.org/reltio-ondemand/reltio-design/src/main/CONTRIBUTING.md). This guide focuses on what happens after a PR is opened — the conceptual flow, semver policy, and operational details.

## Why this design

Three goals shaped the process:

1. **Consumers can see what changed.** Every release ships with a `CHANGELOG.md` entry per affected package, generated automatically from per-PR changesets.
2. **Maintainers control the release cadence.** Versioning happens on-demand through a custom pipeline, not on every merge — which lets the CoE batch related changes, write proper migration notes, and time releases against consumer schedules.
3. **AI agents and humans use the same workflow.** The `.agents/skills/add-changeset/SKILL.md` skill lets Cursor / Claude Code / Copilot CLI author changesets the same way humans do — through the same Changesets CLI, the same markdown frontmatter, the same review gates.

## End-to-end flow

The diagram has three "actors":

- **Developer** — one step (author the change + changeset).
- **CI** — three steps (run PR checks, cut the version PR via `version @reltio packages`, publish via the auto-release on `main`).
- **CoE maintainer** — two steps (trigger `version @reltio packages` when a release is due, review and merge the version PR).

The publish itself is never triggered by hand on a normal release. The maintainer's gate is the **version-PR review** — once that PR merges, the next `branches: main` pipeline picks up the bumped versions and publishes them.

### 1. Author phase (developer)

Each PR carries a `.changeset/*.md` file that describes the intended version bump and the consumer-visible impact. The file is the contributor's _release intent_ — a one-line declaration of "this PR should bump `@reltio/design` by X, and here's what to put in the next release notes". No version bump happens at this point; the file is queued up until a maintainer cuts the release.

The CI step `check-changeset` runs on every PR and fails if `packages/*` source code changed but no new `.changeset/*.md` is committed. The check is heuristic — pure metadata changes (`package.json`, `tsconfig.json`, `README.md`) do not trigger it.

> **For the day-to-day mechanics** — CLI prompts, bump-type table, good/bad summary examples, when to use `--empty` — see [`CONTRIBUTING.md` → Adding a changeset](https://bitbucket.org/reltio-ondemand/reltio-design/src/main/CONTRIBUTING.md#adding-a-changeset).

### 2. Version phase (maintainer)

When the CoE decides to release — typically when there's enough new content, when a consumer is blocked on a fix, or on a regular cadence — a maintainer triggers the custom pipeline **`version @reltio packages`** in Bitbucket against `main`.

The pipeline runs `changeset version`, which:

- Reads every `.changeset/*.md`.
- Bumps `packages/*/package.json` versions according to the highest bump type per package.
- Updates `packages/*/CHANGELOG.md` with sections grouped by bump type.
- Deletes the consumed `.changeset/*.md` files.

It then commits the result onto a new branch `release/version-<timestamp>`, pushes it to origin, and **automatically opens a pull request into `main`** through the Bitbucket REST API. This last step requires a one-time token setup — see [Maintainer setup](#maintainer-setup). Without the token the pipeline still pushes the branch and prints a fallback URL, so a maintainer can open the PR by hand without breaking the workflow.

The auto-generated PR carries a structured description with the list of bumped packages (parsed from the diff against `main`) and post-merge instructions. **This PR is the release review.** Reviewers look at the diff and ask:

- Is the version bump correct? (Sometimes an entry is mis-classified; this is the moment to fix it.)
- Do the CHANGELOG entries read as good release notes?
- Does any `major` change have a migration note linked?
- Are any consumer apps blocked on this release?

### 3. Publish phase (automated)

After the version PR is merged into `main`, the **`branches: main`** pipeline fires like it does after any other merge. Four steps run **in parallel**:

- `test` — Vitest + Playwright + interaction tests
- `chromatic` — visual regression
- `vercel` — deploys the Storybook docs site
- `release-packages` — publishes new `@reltio/*` versions to npm and pushes git tags

The maintainer does **not** need to trigger anything manually.

The `release-packages` step:

1. Installs and builds every workspace.
2. Runs `node scripts/release.mjs`, which iterates every non-private package, asks the npm registry whether each `<name>@<version>` is already published, and publishes the ones that are not from their `dist/` directory.
3. Creates an annotated git tag `<package>@<version>` for each newly published version and pushes the tags.

Because the script asks the registry up-front, it is **safe to run on every main commit** — a ~30-second no-op on regular feature merges (no version bump → nothing to publish) and a real publish on version-PR merges.

#### Why publish in parallel with tests

Version-PR merges change only `packages/*/package.json` versions, `packages/*/CHANGELOG.md`, and consumed `.changeset/*.md` files. **No source code, no tests, no build config**. So a regression that the PR pipeline missed cannot suddenly appear when the version PR is merged — `test` / `chromatic` on `main` would see the same source code they saw on the PR.

Running `release-packages` alongside the other three (rather than gating it on them) buys two things:

- **Faster publishes.** Version-PR merges go live in roughly the time of the longest of the parallel steps, not the sum.
- **Failure isolation.** A Chromatic flake or a Vercel outage no longer blocks `npm publish`, and vice versa — these are independent concerns.

Feature-PR merges are also safe: the version on disk matches what is already on npm → `release-packages` skips publish → exits green regardless of test state.

#### A release is complete when

- All affected packages are visible on the npm registry under the `latest` dist-tag.
- The corresponding git tags exist on `origin/main`.
- `packages/*/CHANGELOG.md` on `main` shows the new section at the top.

#### When the auto-release fails

If `release-packages` itself fails (npm registry outage, transient build flake, expired token, …), re-trigger it manually:

- **Run pipeline → `custom: release @reltio packages`** against `main`.

The script is idempotent — versions already on npm are skipped, only the failing ones are retried. The other parallel steps (`test` / `chromatic` / `vercel`) are independent — if one of them is also failing, fix it separately; it does not block publishing.

## Snapshot releases

Sometimes you need to share a build with a consumer **without bumping `latest`** — to verify a fix end-to-end, to demo a candidate API, or to unblock another team mid-PR.

The custom pipeline **`snapshot @reltio packages`** does this. Triggered from any branch, it:

- Generates a snapshot version like `0.0.0-pr-123-20260512-abcd123` using `changeset version --snapshot`.
- Publishes each affected workspace under the dist-tag `pr-<BITBUCKET_PR_ID>` (override via the `SNAPSHOT_TAG` variable).
- **Does not** consume changeset files, **does not** update `CHANGELOG.md`, **does not** create git tags.

Consumers install snapshots with:

```bash
npm install @reltio/design@pr-123
# or pin the exact snapshot:
npm install @reltio/design@0.0.0-pr-123-20260512-abcd123
```

> **💡 Tip:** Production apps should always track `latest` (or a pinned semver range). Use snapshots only for transient testing — they are not deleted from npm, but they accumulate and clutter the registry. Prefer one snapshot per active testing scenario rather than dozens.

## Versioning policy

We follow [semantic versioning](https://semver.org/) strictly for `@reltio/design`. The mapping from changeset bump to semver:

> **⚠️ Pre-1.0 caveat.** While the package is on `0.x`, semver allows minors to contain breaking changes. In practice we still bump `major` on every breaking change (so `0.5.x → 0.6.x` if breaking) to keep the signal clear. Consumers who pin with `^` should still review release notes carefully until we ship `1.0.0`.

## Maintainer setup

The auto-PR step in `version @reltio packages` calls the Bitbucket REST API, which requires a **Repository Access Token** stored as a secured repository variable. This is a one-time per-repo setup — you only do it once when the platform is first wired up (or when you rotate the token).

### Creating the token

1. Open **Bitbucket → Repository settings → Access tokens → Create Repository Access Token.**
2. Name: `Pipelines - Auto PR` (or any descriptive name).
3. Scope: `pullrequest:write`. No other scopes are required — the token cannot push code, only open PRs.
4. Copy the token. It is shown only once.

### Wiring it into Pipelines

1. Open **Bitbucket → Repository settings → Repository variables → Add variable.**
2. Name: `BITBUCKET_PR_TOKEN`
3. Value: the token from the previous step.
4. **Tick the "Secured" checkbox.** The token is sensitive and must not appear in pipeline logs.

That's it. The next run of `version @reltio packages` will detect the variable and call the REST API instead of printing a fallback URL.

### Graceful degradation

`scripts/open-version-pr.mjs` is intentionally non-fatal:

- If `$BITBUCKET_PR_TOKEN` is unset, the script logs a fallback URL and exits 0 — the pipeline still pushes the branch and finishes green.
- If the API responds with "pull request already exists", the script logs a link to the existing PR and exits 0.
- If the API fails for any other reason (token revoked, Bitbucket outage, …), the script logs the error and the fallback URL, then exits 1 so the failure is visible.

This means the workflow never gets stuck on auto-PR — the worst case is a maintainer opens the PR manually, which is exactly the pre-automation workflow.

### Rotating the token

Repository Access Tokens do not expire automatically. Rotate the token when:

- The CoE maintainer who created it leaves the team.
- Bitbucket flags the token as compromised.
- Your team's secrets-rotation policy says it's time.

To rotate: create a new token, update the value of the `BITBUCKET_PR_TOKEN` variable, then revoke the old token in the Access tokens UI.

## AI-assisted authoring

The skill [`.agents/skills/add-changeset/SKILL.md`](https://bitbucket.org/reltio-ondemand/reltio-design/src/main/.agents/skills/add-changeset/SKILL.md) tells AI agents (Cursor, Claude Code, Copilot CLI, …) how to produce a high-quality changeset for the current PR. It runs the same logic a human would:

1. `git diff` against `origin/main` to see what changed
2. Classify the bump type using a clear rubric
3. Draft a consumer-facing summary
4. Write `.changeset/<name>.md`
5. Run `npm run changeset:check` to verify

**Trigger phrases that activate the skill:**

- "Add a changeset for this PR"
- "What bump type is this change?"
- "Prepare release notes for this branch"
- "CI is failing on changeset:check"

The skill is configured to **never** commit or push on the user's behalf — it produces the file and lets the human decide when to add it to the PR.

## Troubleshooting

### "CI is failing on `changeset:check`"

Run `npm run changeset:check` locally. If it lists files under `packages/*` and there is no matching `.changeset/*.md`, add one with `npm run changeset` (or use the `add-changeset` AI skill).

If the listed files are genuinely doc-only or test-only and you don't think a version bump is warranted, add an empty changeset:

```bash
npm run changeset -- --empty
```

### "I made a typo in a published CHANGELOG entry"

After a release, `CHANGELOG.md` is committed history. Open a follow-up PR that edits the line in place. Don't try to revert — the version is already on npm and consumers may be reading the wrong entry.

### "I published the wrong version"

`scripts/release.mjs` checks the registry before publishing, so re-running the pipeline is safe. To pull a bad release:

1. `npm deprecate '@reltio/design@<bad-version>' "Use <good-version> instead"` — sends a warning when consumers install the bad version. **Never unpublish.** Unpublishing breaks anyone who already installed it.
2. Cut a fix release with a fresh patch/minor bump that supersedes the bad one.
3. Document the issue in the release-history guide (when we add Phase 3).

### "Snapshot version doesn't install"

Snapshots are published under a dist-tag, not `latest`. Use the explicit dist-tag:

```bash
npm install @reltio/design@pr-123
```

If the install resolves to `latest` instead, the dist-tag may have been overwritten by a later snapshot — pin to the exact version:

```bash
npm install @reltio/design@0.0.0-pr-123-20260512-abcd123
```

## Best practices

### For PR authors

1. **Write the changeset before opening the PR.** It forces you to articulate the impact while the context is fresh.
2. **Write for the consumer.** Imagine they will read your summary in a release-notes Slack message at 9 AM. Will they understand what to do?
3. **Default to `major` when unsure between `minor` and `major`.** Better to over-warn than to ship a hidden breaking change.
4. **Include a migration block for every `major`.** A `major` changeset without `**Migration:**` slows down every consumer.

### For maintainers

1. **Don't let `.changeset/` accumulate forever.** Cut a release at least every 2 weeks while there are pending changesets, even if it's only a `patch`.
2. **Read the version PR like a release note.** That's exactly what it is. Edit summaries on the version branch before merging if anything reads poorly.
3. **Hold `major` releases for a planned moment.** Pair them with an MDX migration guide under `guides/migrations/` and announce in `#reltio-design` before publishing.
4. **Keep the publish pipeline boring.** If `release @reltio packages` ever needs manual fixes, that's a bug in `scripts/release.mjs` — fix the script, don't normalise workarounds.

### For consumers

1. **Pin with `^` while on 0.x, with the exact version while pinning a `major`.** Read every release's changelog before upgrading.
2. **Use `overrides` only as a break-glass.** The README of `@reltio/design` explains the supported escape hatch — don't make it your default.
3. **Subscribe to release notifications.** (Phase 3 will add a Slack webhook posting to `#reltio-design-releases`.)
