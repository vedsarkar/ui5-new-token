# Dynamic OAuth Routing

The Reltio OAuth server is moving from a single monolithic endpoint to a multi-environment topology — `auth.reltio.com`, `auth-idev-02.reltio.com`, `auth-test.reltio.com`, and more. Each user's access token is issued by a specific cluster, and only that cluster can introspect or refresh it. A single static `oauthPath` cannot route per session.

This guide explains how `@reltio/auth` solves that automatically for Backend for Frontend (BFF) mounted endpoints (`/checkToken`, `/refreshToken`) and how to opt in for application code that bypasses the BFF.

## TL;DR

- **Apps using the BFF** (`/auth/checkToken`, `/auth/refreshToken`): no changes needed. The router routes per session automatically.
- **Apps that call the Auth server directly**: replace your hardcoded `oauthPath` with the `resolveAuthPath` function exposed on the value returned by `createExpressAuth(config)` / `createNextAuth(config)`. It shares the router's once-derived HMAC key, so there is no extra setup.
- **No new configuration** — no new environment variables, no new operator step. The existing `clientSecret` powers the cookie's HMAC signature.

## How it works

1. **At login time**, the Reltio access token returned by `/callback` carries a non-standard `aurl` claim — the URL of the cluster that issued it (e.g. `https://auth-idev-02.reltio.com`).
2. `callbackHandler` decodes the claim, signs it with HMAC-SHA256 (key derived from `AuthConfig.clientSecret`), and writes a third `HttpOnly` cookie alongside `access_token` and `refresh_token`, named `reltio_aurl`.
3. **Every subsequent `/checkToken` and `/refreshToken` request** through the BFF reads `reltio_aurl`, verifies the MAC, and routes the upstream call to that exact cluster — fail-closed to `AuthConfig.oauthPath` on any failure.
4. **After a successful refresh**, the handler re-derives the cookie from the new access token. If the cluster changed (session was migrated), the cookie tracks. If the new token has no `aurl` claim, the cookie is cleared.
5. **`logout`** clears `reltio_aurl` alongside the existing three cookies.

The cookie is `HttpOnly` + `Secure` + `SameSite=Lax` + `Path=/`. The HMAC key never leaves the BFF.

## Public API — `resolveAuthPath`

```ts
const auth = createExpressAuth(config); // or createNextAuth(config)
auth.resolveAuthPath: (request: Request) => Promise<string>;
```

`createAuth` (and therefore both adapters) derives the HMAC key once at construction time and exposes `resolveAuthPath` on its return value — the **same** function the router uses internally for `/checkToken` and `/refreshToken`. There is no separate factory to construct and no extra key derivation:

- **On request**: reads `reltio_aurl` from the `Cookie` header, runs HMAC verify, and returns the recovered URL. Falls back to `config.oauthPath` on absence, parse failure, tampering, or any other verify failure.
- **Accepts** Express `Request`, Next.js `NextRequest`, or Web `Request` uniformly — same shape used by `getAccessToken` and `getRefreshToken`.

The Express adapter attaches `resolveAuthPath` to the returned `Router`; the Next.js adapter returns it alongside `handlers`. Build the auth value once at server boot (as you already do to mount the router) and reuse `resolveAuthPath` on every request.

## When to use it

Use `resolveAuthPath` in application code that calls the Auth server **directly** — bypassing the auth router's `/checkToken` and `/refreshToken` endpoints. Common cases:

- Token introspection in a backend service that runs separately from the BFF.
- Custom refresh flows for long-running background jobs.
- Direct Auth server calls from any route handler that already has the access token in hand.

**Skip it** if your application only mounts the auth router and dispatches all upstream calls through `/auth/checkToken` and `/auth/refreshToken` — routing is automatic and you don't read this function at all.

## Examples

### Express

```ts
// server/auth.ts
import { createExpressAuth } from "@reltio/auth/express";

export const auth = createExpressAuth({
	oauthPath: process.env.OAUTH_PATH!,
	loginPath: process.env.LOGIN_PATH!,
	clientId: process.env.CLIENT_ID!,
	clientSecret: process.env.CLIENT_SECRET!,
});

app.use("/auth", auth); // mounts the router
```

```ts
// server/routes/checkToken.ts
import { getAccessToken } from "@reltio/auth/utils";
import { auth } from "../auth";

app.post("/api/internal/checkToken", async (req, res, next) => {
	const token = getAccessToken(req);
	if (!token) return res.sendStatus(401);

	const oauthPath = await auth.resolveAuthPath(req);
	const upstream = await fetch(`${oauthPath}/checkToken?token=${token}`, {
		method: "POST",
		headers: { Authorization: `Basic ${basicAuth}` },
	});
	res.status(upstream.status).json(await upstream.json());
});
```

### Next.js App Router — Route Handler

```ts
// auth.ts
import { createNextAuth } from "@reltio/auth/next";

export const { handlers, resolveAuthPath } = createNextAuth({
	oauthPath: process.env.OAUTH_PATH!,
	loginPath: process.env.LOGIN_PATH!,
	clientId: process.env.CLIENT_ID!,
	clientSecret: process.env.CLIENT_SECRET!,
});
```

```ts
// app/api/internal/checkToken/route.ts
import { NextResponse } from "next/server";
import { getAccessToken } from "@reltio/auth/utils";
import { resolveAuthPath } from "../../../../auth";

export async function POST(request: Request) {
	const token = getAccessToken(request);
	if (!token) return new NextResponse(null, { status: 401 });

	const oauthPath = await resolveAuthPath(request);
	const upstream = await fetch(`${oauthPath}/checkToken?token=${token}`, {
		method: "POST",
		headers: { Authorization: `Basic ${basicAuth}` },
	});
	return NextResponse.json(await upstream.json(), { status: upstream.status });
}
```

The module-level `createNextAuth(...)` runs once per server boot, so the HMAC key is derived once and `resolveAuthPath` is reused across the stateless Route Handler invocations.

### Next.js Edge Middleware

```ts
// auth.ts
import { createNextAuth } from "@reltio/auth/next";

export const { resolveAuthPath } = createNextAuth({
	oauthPath: process.env.OAUTH_PATH!,
	loginPath: process.env.LOGIN_PATH!,
	clientId: process.env.CLIENT_ID!,
	clientSecret: process.env.CLIENT_SECRET!,
});
```

```ts
// middleware.ts
import { type NextRequest, NextResponse } from "next/server";
import { resolveAuthPath } from "./auth";

export async function middleware(request: NextRequest) {
	const oauthPath = await resolveAuthPath(request);
	// ... downstream routing decisions based on oauthPath ...
	return NextResponse.next();
}
```

`resolveAuthPath` uses Web Crypto only — no Node built-ins — so it runs unchanged on Edge runtime.

## Gating routes with `checkToken`

`resolveAuthPath` gives you the cluster URL; if all you need is to **introspect the current request's token** and act on the parsed result (role / permission checks), use `checkToken` instead. It is the programmatic sibling of the BFF's `POST /checkToken` route — it reads the access token from the request, routes per session via `resolveAuthPath`, calls the Auth server's introspection endpoint with the once-derived Basic credential, and returns the parsed payload. You no longer hand-roll the wire contract (form encoding, Basic header, `serviceId` / `tenantId`, cluster routing, error normalisation).

```ts
const auth = createExpressAuth(config); // or createNextAuth(config)
auth.checkToken: (
	request: Request,
	opts?: { serviceId?: string; tenantId?: string },
) => Promise<CheckTokenResponse>;
```

Unlike the route, `checkToken` returns the **parsed `CheckTokenResponse` payload** (not an HTTP `Response`) and signals failure by **throwing `RequestError`**. Branch on `isRequestError(error)` and `error.statusCode`:

### Express

```ts
// server/middleware/requireAdmin.ts
import { isRequestError } from "@reltio/auth/utils";
import { auth } from "../auth";

export async function requireAdmin(req, res, next) {
	try {
		const { roles } = await auth.checkToken(req, { serviceId: "MDM" });
		if (!roles.includes("ROLE_ADMIN")) return res.sendStatus(403);
		next();
	} catch (error) {
		if (isRequestError(error)) return res.sendStatus(error.statusCode);
		next(error);
	}
}
```

### Next.js App Router — Route Handler

```ts
// app/api/admin/route.ts
import { isRequestError } from "@reltio/auth/utils";
import { NextResponse } from "next/server";
import { checkToken } from "../../../auth";

export async function GET(request: Request) {
	try {
		const { roles } = await checkToken(request);
		if (!roles.includes("ROLE_ADMIN")) {
			return new NextResponse(null, { status: 403 });
		}
		return NextResponse.json({ ok: true });
	} catch (error) {
		if (isRequestError(error)) {
			return new NextResponse(null, { status: error.statusCode });
		}
		throw error;
	}
}
```

Like `resolveAuthPath`, `checkToken` shares the router's once-derived Basic credential and HMAC key — build the auth value once at server boot and reuse it.

## Fail-closed behaviour

Every failure mode falls back silently to `config.oauthPath`. No throws, no error logs, no response codes — the routing decision is invisible from the application layer.

## Security model

- **HMAC key**: SHA-256 of the ASCII concatenation `"reltio-auth-routing-v1:" + clientSecret`. The salt prefix scopes the key to this exact use, so a future feature deriving a different key from `clientSecret` cannot collide with it.
- **MAC length**: full 32-byte HMAC-SHA-256 tag. Verification goes through `crypto.subtle.verify`, which is constant-time by Web Crypto spec — no hand-rolled comparison code to own.
- **Cookie attributes**: byte-identical to `access_token` and `refresh_token` — `HttpOnly`, `Secure` (when `AuthConfig.secure === true`), `SameSite=Lax`, `Path=/`.
- **Bounded decompression in `decodeAurl`** — four layered guards anchored to a single 8 KiB ceiling (encoded-segment cap before base64url decode, declared-size gate, compressed-input cap, bounded output buffer).
- **No SSRF surface**: the signed cookie is the only routing input. A forged JWT in the `access_token` cookie cannot influence routing — `decodeAurl` runs ONLY at `/callback` (mint) and `/refreshToken` (re-mint) write time, never on the hot path.
