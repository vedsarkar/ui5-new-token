# Dynamic OAuth Routing

The Reltio OAuth server is moving from a single monolithic endpoint to a multi-environment topology — `auth.reltio.com`, `auth-idev-02.reltio.com`, `auth-test.reltio.com`, and more. Each user's access token is issued by a specific cluster, and only that cluster can introspect or refresh it. A single static `oauthPath` cannot route per session.

This guide explains how `@reltio/auth` solves that with an **allowlist** of trusted clusters, both for Backend for Frontend (BFF) mounted endpoints (`/checkToken`, `/refreshToken`) and for application code that bypasses the BFF.

## TL;DR

- **Configure the allowlist**: list every additional trusted cluster in `AuthConfig.authEnvironments`. Each entry carries that cluster's own `oauthPath` / `clientId` / `clientSecret`. The same config serves BFFs and standalone API services (which introspect via `auth.checkToken` and may omit `loginPath`).
- **Apps using the BFF** (`/auth/checkToken`, `/auth/refreshToken`): no per-request code needed. The router reads the access token's `aurl` claim and routes to the matching allowlisted cluster automatically.
- **Apps that call the Auth server directly**: use the `resolveAuthPath` function exposed on the value returned by `createExpressAuth(config)` / `createNextAuth(config)` — the same allowlist resolution the router uses internally.

## How it works

1. The Reltio access token carries a non-standard `aurl` claim — the URL of the cluster that issued it (e.g. `https://auth-idev-02.reltio.com`).
2. On every `/checkToken` and `/refreshToken` request, the router reads the access token (from `Authorization: Bearer` or the `access_token` cookie), **decodes** its `aurl` claim, and matches it — by normalized origin, trailing-slash insensitive — against the allowlist (the primary `oauthPath` plus every `authEnvironments[].oauthPath`).
3. On a match, the upstream call goes to **that cluster's** auth server, authenticated with **that cluster's** `clientId` / `clientSecret`.
4. An `aurl` that is absent, undecodable, or **not in the allowlist** falls back to the primary cluster (`oauthPath`).

> **🎯 Key Principle:** The `aurl` claim can only ever *select* a pre-configured cluster from the allowlist — it can never introduce an arbitrary outbound origin. A forged token cannot steer the BFF to an attacker-controlled URL.

## Configuration — the allowlist

Add every additional trusted cluster to `authEnvironments`. The primary cluster is always the top-level `oauthPath` + `clientId` / `clientSecret`; each additional environment shares the same `{ oauthPath, clientId, clientSecret }` shape.

```ts
import { createExpressAuth } from "@reltio/auth/express";

export const auth = createExpressAuth({
	oauthPath: "https://auth.reltio.com",
	loginPath: "https://login.reltio.com",
	clientId: process.env.CLIENT_ID!,
	clientSecret: process.env.CLIENT_SECRET!,
	authEnvironments: [
		{
			oauthPath: "https://auth-idev-02.reltio.com",
			clientId: process.env.IDEV02_CLIENT_ID!,
			clientSecret: process.env.IDEV02_CLIENT_SECRET!,
		},
	],
});
```

- Omit `authEnvironments` for a single-cluster deployment — every request routes to `oauthPath` as before.
- A malformed `authEnvironments[].oauthPath` throws at construction time (fail-fast), so a misconfiguration surfaces at boot rather than silently on a request.
- If an additional service duplicates the primary origin, the primary's credentials win.

## Public API — `resolveAuthPath`

```ts
const auth = createExpressAuth(config); // or createNextAuth(config)
auth.resolveAuthPath: (request: Request) => Promise<string>;
```

`createAuth` (and therefore both adapters) builds the allowlist once at construction time and exposes `resolveAuthPath` on its return value — the **same** resolution the router uses internally for `/checkToken` and `/refreshToken`:

- **On request**: reads the access token, decodes its `aurl` claim, and returns the matching allowlisted cluster's `/oauth` path. Falls back to `config.oauthPath` when the token is absent, undecodable, or its `aurl` is not in the allowlist.
- **Accepts** Express `Request`, Next.js `NextRequest`, or Web `Request` uniformly — same shape used by `getAccessToken` and `getRefreshToken`.

The Express adapter attaches `resolveAuthPath` to the returned `Router`; the Next.js adapter returns it alongside `handlers`. Build the auth value once at server boot (as you already do to mount the router) and reuse `resolveAuthPath` on every request.

## When to use it

Use `resolveAuthPath` in application code that calls the Auth server **directly** — bypassing the auth router's `/checkToken` and `/refreshToken` endpoints. Common cases:

- Token introspection in a backend service that runs separately from the BFF.
- Custom refresh flows for long-running background jobs.
- Direct Auth server calls from any route handler that already has the access token in hand.

**Skip it** if your application only mounts the auth router and dispatches all upstream calls through `/auth/checkToken` and `/auth/refreshToken` — routing is automatic and you don't read this function at all.

## Examples

### Express

```ts
// server/auth.ts
import { createExpressAuth } from "@reltio/auth/express";

export const auth = createExpressAuth({
	oauthPath: "https://auth.reltio.com",
	loginPath: "https://login.reltio.com",
	clientId: process.env.CLIENT_ID!,
	clientSecret: process.env.CLIENT_SECRET!,
	authEnvironments: [
		{
			oauthPath: "https://auth-idev-02.reltio.com",
			clientId: process.env.IDEV02_CLIENT_ID!,
			clientSecret: process.env.IDEV02_CLIENT_SECRET!,
		},
	],
});

app.use("/auth", auth); // mounts the router
```

```ts
// server/routes/checkToken.ts
import { getAccessToken } from "@reltio/auth/utils";
import { auth } from "../auth";

app.post("/api/internal/checkToken", async (req, res, next) => {
	const token = getAccessToken(req);
	if (!token) return res.sendStatus(401);

	const oauthPath = await auth.resolveAuthPath(req);
	const upstream = await fetch(`${oauthPath}/checkToken?token=${token}`, {
		method: "POST",
		headers: { Authorization: `Basic ${basicAuth}` },
	});
	res.status(upstream.status).json(await upstream.json());
});
```

		},

```ts
// app/api/internal/checkToken/route.ts
import { NextResponse } from "next/server";
import { getAccessToken } from "@reltio/auth/utils";
import { resolveAuthPath } from "../../../../auth";

export async function POST(request: Request) {
	const token = getAccessToken(request);
	if (!token) return new NextResponse(null, { status: 401 });

	const oauthPath = await resolveAuthPath(request);
	const upstream = await fetch(`${oauthPath}/checkToken?token=${token}`, {
		method: "POST",
		headers: { Authorization: `Basic ${basicAuth}` },
	});
	return NextResponse.json(await upstream.json(), { status: upstream.status });
}
```

The module-level `createNextAuth(...)` runs once per server boot, so the allowlist is built once and `resolveAuthPath` is reused across the stateless Route Handler invocations.

## Gating routes with `checkToken`

`resolveAuthPath` gives you the cluster URL; if all you need is to **introspect the current request's token** and act on the parsed result (role / permission checks), use `checkToken` instead. It is the programmatic sibling of the BFF's `POST /checkToken` route — it reads the access token from the request, resolves the issuing cluster from the token's `aurl` claim + allowlist, calls that cluster's introspection endpoint with that cluster's Basic credential, and returns the parsed payload. You no longer hand-roll the wire contract (form encoding, Basic header, `serviceId` / `tenantId`, cluster routing, error normalisation).

```ts
const auth = createExpressAuth(config); // or createNextAuth(config)
auth.checkToken: (
	request: Request,
	opts?: { serviceId?: string; tenantId?: string },
) => Promise<CheckTokenResponse>;
```

Unlike the route, `checkToken` returns the **parsed `CheckTokenResponse` payload** (not an HTTP `Response`) and signals failure by **throwing `RequestError`**. Branch on `isRequestError(error)` and `error.statusCode`:

### Express

```ts
// server/middleware/requireAdmin.ts
import { isRequestError } from "@reltio/auth/utils";
import { auth } from "../auth";

export async function requireAdmin(req, res, next) {
	try {
		const { roles } = await auth.checkToken(req, { serviceId: "MDM" });
		if (!roles.includes("ROLE_ADMIN")) return res.sendStatus(403);
		next();
	} catch (error) {
		if (isRequestError(error)) return res.sendStatus(error.statusCode);
		next(error);
	}
}
```

### Next.js App Router — Route Handler

```ts
// app/api/admin/route.ts
import { isRequestError } from "@reltio/auth/utils";
import { NextResponse } from "next/server";
import { checkToken } from "../../../auth";

export async function GET(request: Request) {
	try {
		const { roles } = await checkToken(request);
		if (!roles.includes("ROLE_ADMIN")) {
			return new NextResponse(null, { status: 403 });
		}
		return NextResponse.json({ ok: true });
	} catch (error) {
		if (isRequestError(error)) {
			return new NextResponse(null, { status: error.statusCode });
		}
		throw error;
	}
}
```

Like `resolveAuthPath`, `checkToken` shares the router's once-built allowlist — build the auth value once at server boot and reuse it.

## Fail-open-to-primary behaviour

Every routing miss falls back silently to `config.oauthPath`. No throws, no error logs, no response codes — the routing decision is invisible from the application layer.

## Security model

- **Allowlist is the trust boundary.** The `aurl` claim only *selects* an entry from the operator-configured allowlist (the primary `oauthPath` + `authEnvironments`). It can never introduce an origin the operator did not configure, so a forged or attacker-controlled `aurl` closes off the SSRF surface entirely — the worst case is a fallback to the primary cluster.
- **Credentials are per-cluster.** Each allowlisted cluster introspects and refreshes with its own `clientId` / `clientSecret`; a token routed to a cluster is authenticated with that cluster's credentials, never a shared one.
- **No local signature verification (this version).** `aurl` is trusted purely through allowlist membership — the token signature is not verified locally. Because the allowlist bounds every possible outbound origin, an unverified `aurl` cannot escalate beyond selecting a pre-approved cluster. Local signature verification (to remove the per-service allowlist) is a possible future addition.
- **Bounded decompression in `decodeAccessToken`** — layered guards (encoded-segment cap before base64url decode, declared-size gate, compressed-input cap, bounded output buffer) ensure a hostile token cannot amplify into a decompression bomb while its `aurl` is extracted.
