# Spec-Driven Development Guide

Welcome to the Reltio Design Platform's spec-driven development workflow. This guide explains how we use **OpenSpec (OPSX)** with **Claude Skills** to ensure predictable, high-quality component development. The skills work across both **Cursor IDE** and **Claude Code**, giving every AI agent the same workflow capabilities.

## What is Spec-Driven Development?

> **Note:** This video demonstrates Spec-Kit framework (by GitHub), but we've decided to use OpenSpec — a lighter alternative with flexible iteration instead of rigid phase gates. The core SDD concepts remain the same.

Spec-Driven Development (SDD) is a methodology where **specifications come before implementation**. Instead of jumping straight into code, you first describe what you're building, why it matters, and how it should behave. Only then do you write the code that fulfills those specifications.

This approach becomes especially powerful with AI-assisted development:

- **AI needs clear instructions** — Vague requests lead to vague implementations. Detailed specs give AI the context it needs to generate accurate code.
- **Humans need shared understanding** — Specs create a single source of truth that developers, designers, and stakeholders can review before code exists.
- **Changes need traceability** — When every change has a proposal and spec, you can always answer "why was this built this way?"

> **Key Principle:** We specify before we build. Work flows through artifacts—proposal, specs, design, tasks—with dependencies guiding progress, not rigid phases. This enables iteration while maintaining clarity.

## Core Concepts

### Actions, Not Phases

OPSX uses an action-based approach. Instead of rigid phases that lock you into a sequence, you perform actions on a change based on artifact dependencies. This means you can:

- Update a proposal after starting design
- Refine specs during implementation
- Explore at any point when clarity is needed

Dependencies guide what's possible, not what's mandatory.

### Artifact Flow

Every change produces artifacts in a dependency order:

```
proposal → specs → design → tasks
```

- **Proposal** — Why we're making this change and what it involves
- **Specs** — Detailed requirements with testable scenarios
- **Design** — Technical decisions and implementation approach
- **Tasks** — Implementation checklist that drives coding

Each artifact unlocks the next. You can't create tasks without understanding what you're building (specs) and how you'll build it (design).

### Brownfield-First

OpenSpec is designed with a **brownfield-first** philosophy — it works with existing codebases, not just greenfield projects. Most software work isn't building from scratch; it's modifying existing systems. OpenSpec uses delta-based specifications that capture only what's changing (ADDED, MODIFIED, REMOVED requirements), eliminating the burden of restating unchanged specifications.

This makes OpenSpec suitable for any project — not just this design platform. Other teams and repositories at Reltio can adopt this workflow to bring the same benefits of clarity, traceability, and AI-assisted development to their existing codebases.

## Bottom-Up Development: From Components to Features

One of the most important principles in spec-driven development is **decomposition** — breaking large features into small, focused changes. We call this the **bottom-up approach**: build foundational components first, then compose them into larger features.

> **🧩 Core Principle:** Ten simple changes are better than one complex change. Each small change is easier to specify, implement, review, and verify.

### Real Example: Building a Product Page

**❌ Don't:** Create one massive change

```
/openspec-new-change create a Product Page with header, image gallery,
price section, add-to-cart button, reviews section, and related products
```

This creates a massive change that is hard for AI to implement correctly, takes days to review, has dozens of interconnected tasks, is impossible to estimate accurately, and cannot be deployed incrementally.

**✅ Do:** Decompose into focused changes

First, use explore mode to help decompose:

```
/openspec-explore Help me decompose a Product Page into individual component changes.
I need: header, image gallery, price, cart button, reviews, related products.
```

Then create changes in order, from specific to general:

```
# Phase 1: Foundation components (can run in parallel)
/openspec-new-change add-product-image
/openspec-new-change add-price-display
/openspec-new-change add-cart-button
/openspec-new-change add-star-rating

# Phase 2: Composite components (after Phase 1)
/openspec-new-change add-image-gallery
/openspec-new-change add-review-card
/openspec-new-change add-reviews-list

# Phase 3: Page assembly (after Phase 2)
/openspec-new-change add-product-page
```

**Result:** 8 simple changes instead of 1 complex one. Each can be:
- Implemented in hours, not days
- Reviewed in minutes
- Tested independently
- Deployed incrementally
- Reused in other pages

### Benefits for Developers

1. **Faster implementation** — AI completes small tasks with higher accuracy
2. **Easier debugging** — When something breaks, you know exactly where
3. **Better testing** — Each component has isolated, focused tests
4. **Cleaner code** — Small scope naturally leads to clean architecture
5. **Learning opportunity** — New developers can start with simple changes

### Benefits for Managers

1. **Accurate estimates** — Small tasks are predictable
2. **Visible progress** — See completions daily, not weekly
3. **Lower risk** — Problems are caught early and isolated
4. **Flexible prioritization** — Can reorder or pause without losing work
5. **Better resource allocation** — Parallel work on independent changes

### How to Decompose Effectively

Use explore mode to help with decomposition:

```
/openspec-explore I want to build [feature]. Help me break it down into the smallest
possible independent components that I can create as separate changes.
Order them from most fundamental (no dependencies) to most composite.
```

**Signs your change is too big:**
- More than 10 tasks in `tasks.md`
- Touches more than 3-4 files
- Takes more than 1 day to implement
- Hard to describe in one sentence
- Contains the word "and" multiple times in the title

**Signs your change is right-sized:**
- 3-7 focused tasks
- Single responsibility
- Can be implemented and verified in hours
- Easy to explain in one sentence
- Creates one reusable artifact

> **Remember:** The goal is not to create more work, but to create *manageable* work. Ten simple changes are less total effort than one complex change that requires multiple rewrites.

## Claude Skills Integration

OpenSpec uses **Claude Skills** (`SKILL.md` files) to power the workflow. Skills are stored in `.claude/skills/` and are compatible with both **Cursor IDE** and **Claude Code** — any AI agent with access to the repository automatically gains the full OpenSpec workflow.

### How Skills Work

Every skill can be invoked via a **slash command** — this is the recommended approach for reliability and predictability. You can also describe your intent in natural language, and the AI agent will select the appropriate skill automatically.

```
# Recommended: explicit command invocation
/openspec-explore real-time collaboration
/openspec-new-change add-icon-button
/openspec-continue-change add-icon-button
/openspec-ff-change add-icon-button
/openspec-apply-change add-icon-button
/openspec-verify-change add-icon-button
/openspec-archive-change add-icon-button
```

> **Recommended:** Use slash commands for consistent, predictable behavior. Natural language works too — the AI will match your intent to the right skill — but explicit commands remove ambiguity.

### Skill Architecture

Skills live in `.claude/skills/` and each has a `SKILL.md` file that instructs the AI agent how to perform the action:

```
.claude/skills/
├── openspec-explore/SKILL.md
├── openspec-new-change/SKILL.md
├── openspec-continue-change/SKILL.md
├── openspec-ff-change/SKILL.md
├── openspec-apply-change/SKILL.md
├── openspec-verify-change/SKILL.md
├── openspec-archive-change/SKILL.md
├── openspec-sync-specs/SKILL.md
├── openspec-bulk-archive-change/SKILL.md
└── openspec-onboard/SKILL.md
```

### Core Skills

#### Explore — Think Through Problems

Use when you need to think through an idea, investigate a problem, or clarify requirements before starting work.

```
/openspec-explore real-time collaboration
```

**What happens:**
1. AI enters thinking partner mode
2. Explores the codebase for relevant context
3. Uses ASCII diagrams to visualize concepts
4. Suggests directions without forcing structure

Explore mode is for thinking, not implementing. You can exit anytime and transition to creating a change when ready.

#### New + Continue — Recommended Workflow

This is the primary workflow for creating changes. It builds artifacts one at a time, giving you the opportunity to review and refine each one before moving forward.

**Start a new change:**

```
/openspec-new-change add-icon-button
```

**Continue building artifacts:**

```
/openspec-continue-change add-icon-button
```

**What happens:**
1. `/openspec-new-change` creates the change directory and shows the proposal template
2. You review and refine each artifact before proceeding
3. `/openspec-continue-change` creates the next artifact based on dependencies
4. Repeat until all artifacts are complete

This deliberate pace ensures each artifact gets proper attention. Specs inform design, design informs tasks — reviewing at each step catches issues early.

> **Recommended:** Use this workflow for all changes. The few extra minutes spent reviewing artifacts saves hours of rework during implementation.

#### Fast-Forward (Use Sparingly)

Generates all planning artifacts at once. Useful when you have a very clear picture of what you want and need to move quickly.

```
/openspec-ff-change add-icon-button
```

**When to use:**
- Small, well-understood changes
- Prototyping or exploring ideas quickly
- You're confident in the requirements

**When to avoid:**
- Complex features with multiple capabilities
- Changes that affect existing behavior
- When requirements need discussion

> **Caution:** Skipping artifact review can lead to misaligned implementation. If you use `/openspec-ff-change`, take time to review the generated artifacts before running `/openspec-apply-change`.

#### Apply — Implement Tasks

Use after artifacts are complete and you're ready to generate code.

```
/openspec-apply-change add-icon-button
```

**What happens:**
1. Reads all artifacts for context
2. Implements tasks sequentially
3. Marks checkboxes as work completes
4. Pauses on blockers or unclear requirements

> **Important:** Always review artifacts before running `/openspec-apply-change`. The AI implements exactly what's specified.

#### Verify — Validate Implementation

Use before archiving to ensure implementation matches specifications.

```
/openspec-verify-change add-icon-button
```

**What happens:**
1. Checks task completion status
2. Verifies requirements are implemented
3. Confirms scenarios are covered
4. Validates design decisions were followed
5. Reports issues by priority (critical, warning, suggestion)

#### Archive — Complete the Change

Use after implementation is verified and deployed.

```
/openspec-archive-change add-icon-button
```

**What happens:**
1. Checks for incomplete artifacts or tasks
2. Offers to sync specs to main spec directory
3. Moves change to `openspec/changes/archive/YYYY-MM-DD-<name>/`
4. Creates a permanent changelog record

### Project Changelog

The archive directory (`openspec/changes/archive/`) serves as the project changelog. Each archived change contains:

- **proposal.md** — The original motivation and scope
- **specs/** — The requirements that were added or modified
- **design.md** — Technical decisions and approach
- **tasks.md** — What was implemented

Browse the archive to understand project history:

```
openspec/changes/archive/
├── 2025-12-15-add-button-component/
├── 2025-12-20-add-treelist-component/
└── 2026-01-10-update-button-variants/
```

## AI-Assisted Development Workflow

Working with AI follows a collaborative pattern:

### 1. Explore First

When facing unclear requirements or complex problems, start with explore mode:

```
/openspec-explore I want to add real-time collaboration to the editor.
What approaches should I consider?
```

Explore mode is your thinking partner. It investigates the codebase, visualizes architecture, and helps clarify requirements without committing to a direction.

### 2. Describe Intent Clearly

Be specific about what you want. Good prompts include:

- **Context** — What component or feature area
- **Goal** — What you want to achieve
- **Constraints** — Any limitations or requirements

**✅ Do:** Write focused, specific prompts

```
/openspec-new-change add-icon-button
# Then describe: "IconButton extends Button with left/right icon positions"
```

**❌ Don't:** Write vague, broad prompts

```
/openspec-new-change make-button-better
```

**✅ Do:** Reference existing patterns

```
"Add loading state to Button, similar to how disabled state is handled"
```

**❌ Don't:** Start from scratch every time

```
"Create a disabled state" (without context)
```

### 3. Review Artifacts Before Implementing

Always review AI-generated artifacts before running apply:

- Check proposal captures your intent
- Verify specs cover edge cases
- Ensure design decisions make sense
- Confirm tasks are complete and ordered correctly

**✅ Do:** Review artifacts before applying

```
Read proposal.md → Check specs/ → Review design.md → Run /openspec-apply-change
```

**❌ Don't:** Apply without review

```
Run /openspec-apply-change immediately after creating artifacts
```

### 4. Iterate on Artifacts

OPSX supports fluid iteration. Don't hesitate to update artifacts:

```
The spec looks good, but please add a scenario
for the loading state with custom spinner
```

You can update any artifact at any point—the workflow isn't phase-locked.

### 5. Verify Before Archiving

After implementation, run verification:

```
/openspec-verify-change add-icon-button
```

This ensures:
- All tasks are marked complete
- Requirements are implemented
- Scenarios are covered
- Design decisions were followed

Fix any critical issues before archiving.

## Best Practices

### For New Developers

1. **Run the onboarding** — Use `/openspec-onboard` to learn the workflow with real work
2. **Start with small changes** — Get familiar with the workflow on simple tasks
3. **Read existing specs** — Look at `openspec/specs/` to understand the format
4. **Use explore mode freely** — It's safe for thinking without side effects
5. **Don't skip review** — Always read artifacts before applying

### For Experienced Developers

1. **Use explore for complex problems** — Even experts benefit from structured thinking
2. **Reference existing patterns** — Point the AI to similar components
3. **Break large changes** — Multiple smaller changes are better than one huge one
4. **Verify before archiving** — Use `/openspec-verify-change` to catch issues
5. **Archive promptly** — Don't let completed changes linger

### For Stakeholders

1. **Review proposal.md** — Understand what's changing and why
2. **Check design.md** — See technical decisions and tradeoffs
3. **Browse the archive** — Understand project history and decisions

## Troubleshooting

### "The AI doesn't understand my request"

- Use explore mode first to think through the problem
- Be more specific about the component and behavior
- Reference existing components: "Similar to how Button handles disabled state"
- Break the request into smaller parts

### "Artifacts are missing something"

- Update the artifact directly — the workflow isn't phase-locked
- Ask for modifications: "Please also add [missing requirement]"
- Point to existing specs: "Include scenarios like in button-component spec"

### "Implementation doesn't match the spec"

- Run `/openspec-verify-change` to identify specific issues
- Review the spec — maybe it needs clarification
- Update artifacts and re-run affected tasks
- Manually adjust and update the spec to match

### "I'm not sure if this needs a change"

When in doubt, create a change. It's quick to create and provides:
- Clear documentation of what's changing
- A review checkpoint before coding
- A record in the changelog

### "I need to update an artifact after starting implementation"

This is normal and expected. OPSX supports fluid iteration:
- Update the artifact directly
- Run `/openspec-verify-change` to check alignment
- Continue implementation with updated context

## Configuration

Project-level configuration lives in `openspec/config.yaml`:

```yaml
schema: spec-driven

# Project context injected into all artifacts
context: |
  Tech stack: React 17+, TypeScript, CSS Modules
  We use design tokens for styling

# Per-artifact rules
rules:
  proposal:
    - Keep proposals under 500 words
    - Always include a "Non-goals" section
  tasks:
    - Break tasks into chunks of 3-7 items
```

Context is shown to AI when creating any artifact. Rules apply only to their matching artifact type.
