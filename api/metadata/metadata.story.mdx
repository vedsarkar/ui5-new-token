# Reltio Tenant Metadata Configuration

Root configuration object (also known as L3) that defines the complete data model for a Reltio MDM tenant. This is the single source of truth for all business entities, relationships, matching logic, survivorship rules, and data governance within a tenant.

Every piece of data stored in Reltio — profiles, relationships, interactions, groups — is shaped by this configuration. All UI applications, integrations, ETL pipelines, and AI agents must read and interpret this object to understand the tenant's data model. Returned by GET /reltio/api/\{tenantId\}/configuration and updated via PUT to the same endpoint.

### `uri`

- **Type:** `string`
- **Required**

Resource identifier path for the configuration object. For the root configuration, this is always the literal string "configuration". Child objects within the configuration use hierarchical URIs that extend this root (e.g. "configuration/entityTypes/Person", "configuration/sources/CRM"). The URI serves as the primary key for all configuration objects and is used extensively in cross-references between types.

### `description`

- **Type:** `string`

Human-readable description of this configuration. Typically a brief summary of the data model's purpose or the tenant it serves. In development environments, this field is sometimes used as an informal changelog.

### `label`

- **Type:** `string`

Display name of the data model configuration, shown in administrative UIs such as Reltio Console and Data Modeler.

### `schemaVersion`

- **Type:** `string`
- **Required**

Version of the Reltio Configuration API schema format. This is not a tenant-specific version — it indicates which generation of the configuration schema structure is used. The Reltio platform uses this value to apply the correct parsing and validation logic. Incrementing this value may unlock newer configuration capabilities.

### `abstract`

- **Type:** `boolean`
- **Default:** `false`

When true, this configuration acts as a base template (known as a "vertical") and cannot be directly assigned to a tenant. Abstract configurations define shared entity types, relation types, and rules that are inherited by downstream configurations via referenceConfigurationURI. This enables a layered architecture: platform defaults (L1) → vertical templates (L2) → tenant-specific overrides (L3).

### `referenceConfigurationURI`

- **Type:** `string`

URI of the parent configuration that this one extends. Enables configuration inheritance: the current configuration merges with and overrides properties from the referenced parent. Typically points to a vertical (abstract) configuration like "configuration/_vertical/healthcare-core". When reading the effective configuration, use GET with inheritance to see the fully resolved result; when editing, use GET with _noinheritance to modify only the tenant-specific L3 layer.

### `createdTime`

- **Type:** `number`
- **Read-only**

Server-generated Unix timestamp in milliseconds indicating when this configuration was first created. Read-only — set automatically by the platform and not accepted in PUT/POST requests.

### `updatedTime`

- **Type:** `number`
- **Read-only**

Server-generated Unix timestamp in milliseconds of the last modification to this configuration. Read-only — updated automatically by the platform on every successful PUT.

### `createdBy`

- **Type:** `string`
- **Read-only**

Username or email of the user who initially created this configuration. Read-only — set automatically by the platform based on the authenticated caller.

### `updatedBy`

- **Type:** `string`
- **Read-only**

Username or email of the user who last modified this configuration. Read-only — updated automatically by the platform on every successful PUT.

### `sources`

- **Type:** `array<unknown>`

Registry of all source systems that contribute data to this tenant. Every crosswalk (source-specific record identifier) on every entity and relationship must reference a source defined here. Sources represent upstream systems such as CRMs, ERPs, data vendors, ETL pipelines, or manual entry channels.

Sources play a critical role in survivorship: when multiple sources provide conflicting values for the same attribute, survivorship rules use source identity and optional priority to determine the winning value on the golden record. System-reserved sources like "Reltio", "ReltioCleanser", and "ReltioGrouping" are used internally for platform-generated data.

### `attributeTypes`

- **Type:** `array<unknown>`

Global reusable attribute type definitions that establish shared matching and comparison behavior. Each attribute type (e.g. AddressLine, PhoneNumber, Email, OrganizationName) specifies a value type and optional Java classes for match tokenization and comparison.

These are not the attributes themselves — they are templates. Individual attributes within entityTypes or relationTypes reference these types to inherit their matching logic. For example, an attribute with attributeTypeURI pointing to "configuration/attributeTypes/PhoneNumber" will use phone-number-aware tokenization and fuzzy comparison during match rule evaluation.

### `entityTypes`

- **Type:** `array<unknown>`
- **Required**

The core of the data model — definitions of all business entity types stored in this tenant. Each entity type (e.g. Person, Organization, Product, Location) is a complete specification that includes: attributes (simple, nested, and reference), match rules for duplicate detection, survivorship groups for golden record assembly, display label patterns, visual styling (color, icons), lifecycle actions, cleanse configuration, and search/facet settings.

Entity types support single inheritance via extendsTypeURI — a child type inherits all attributes, match rules, and survivorship from its parent and can add or override them. Abstract entity types (abstract: true) serve as base types that cannot be instantiated directly. Every record (profile) in Reltio is an instance of exactly one entity type defined here.

### `relationTypes`

- **Type:** `array<unknown>`

Definitions of relationship types that connect exactly two entities. Each relation type (e.g. EmployedBy, HasAddress, AffiliatedWith) specifies a startObject and endObject — each pointing to an entity type URI or a role URI — along with direction (directed/undirected), whether the relation is implicit, and its own set of attributes and survivorship rules.

Relations can carry their own attributes (e.g. "start date", "role") and have independent survivorship. They support inheritance via extendsTypeURI, allowing base relation types to be extended with additional attributes. The implicit flag indicates whether the platform auto-creates reverse relations. Relation types also define the edges available in graphTypes.

### `interactionTypes`

- **Type:** `array<unknown>`

Definitions of interaction (event) types that involve multiple entities simultaneously. Unlike relations which connect exactly two entities, interactions model multi-party events such as meetings, calls, prescriptions, or transactions. Each interaction type defines member types with cardinality constraints (minOccurs) — for example, a Meeting might require at least one organizer and one participant.

Interactions have their own attributes (e.g. date, notes, location) and are stored as first-class objects in Reltio with their own lifecycle.

### `groupTypes`

- **Type:** `array<unknown>`

Definitions of group types for clustering entities into named collections. Groups (e.g. Household, Account Team) aggregate multiple entities with optional primary member designation. Each group type configures: whether a primary member is required, whether multiple primary members are allowed, whether an entity can belong to only one group instance, group-specific attributes, member types with labels, and which entity types can participate.

Groups have their own display label patterns that can reference primary member attributes (e.g. "[primaryMember](\{LastName\}) Household"). The type field distinguishes manual groups from system-managed ones.

### `graphTypes`

- **Type:** `array<unknown>`

Definitions of logical graph structures that organize entities connected by specified relationship types into visual and navigable networks. Each graph type (e.g. Family Graph, Org Chart) specifies which relation types form its edges, the graph structure (network or tree), layout style (family, hierarchical), and whether cycles are permitted.

Graphs are a presentation-layer concept — they don't create new data, but define how existing entities and relations are visualized and traversed in graph-based UI views.

### `hierarchyTypes`

- **Type:** `array<unknown>`

Definitions of hierarchical tree structures for organizing entities into parent-child taxonomies. Unlike graphTypes which visualize relationship networks, hierarchies enforce strict tree structures. Each hierarchy type can optionally restrict which entity types are allowed as members via allowedEntityTypes.

Hierarchies are used for organizational structures, geographic trees, product catalogs, and similar tree-shaped classifications.

### `categoryTypes`

- **Type:** `array<unknown>`

Definitions of category (classification) taxonomies that can be applied to entities. Each category type defines its own attributes (e.g. Name), a display label pattern, and which entity types can be categorized via acceptableEntityTypes.

Categories provide a tagging/classification mechanism orthogonal to entity type hierarchy — for example, a Product entity might be classified into multiple category trees simultaneously.

### `roles`

- **Type:** `array<unknown>`

Role definitions used for entity classification and relation endpoint specification. Roles (e.g. Client, Advisor, PracticeManager) serve two purposes: (1) entity types reference roles via entityTypeRoleURIs to classify entity instances — e.g. an Individual can be tagged as a "Client" or "Advisor"; (2) relation type startObject/endObject can reference a role URI instead of a specific entity type, allowing any entity type with that role to participate in the relation.

Each role has a URI, label, and optional description. Roles are lightweight classification markers — they carry no attributes or behavior of their own.

### `survivorshipStrategies`

- **Type:** `array<unknown>`

Named survivorship strategies that determine how the platform selects the winning attribute value when multiple sources provide conflicting data for the same attribute on a golden record. Each strategy encodes a different resolution algorithm: Recency (most recently updated value wins), Frequency (most common value wins), Aggregation (all values are kept), Source System (value from a preferred source wins), Min/Max Value, Oldest Value, or Cleanser-wins (value from ReltioCleanser source takes priority).

Entity types and relation types reference these strategies by URI in their survivorshipGroups to assign specific strategies to specific attributes or attribute groups.

### `changeRequestTypes`

- **Type:** `array<unknown>`

Definitions of change request workflows for governed data modifications. When enabled, edits to golden record data go through an approval process instead of being applied immediately. Each change request type defines the workflow configuration.

This is part of Reltio's data stewardship and governance capabilities, ensuring that sensitive data changes are reviewed and approved before taking effect.
