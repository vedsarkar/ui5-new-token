# Login Page

> **Repository:** `reltio-ondemand/login-page`

The Login Page is the central SSO gateway for all Reltio products. It handles username/password authentication, SSO provider discovery, multi-factor authentication (TOTP), password reset, and tenant selection. It runs as a full-stack Next.js application backed by an Express server that proxies authentication requests to the Reltio OAuth service.

## Authentication Flows

<table>
  <thead>
    <tr>
      <th>Flow</th>
      <th>Entry point</th>
      <th>Description</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>Username / Password</td>
      <td><code>GET /</code></td>
      <td>Credentials are validated server-side via <code>/services/login</code>, which proxies to the Reltio OAuth service. On success a short-lived login code is returned and the user is redirected to the configured <code>redirect_uri</code>.</td>
    </tr>
    <tr>
      <td>SSO (corporate login)</td>
      <td><code>GET /</code> with <code>skipReltioLogin=false</code></td>
      <td><code>/services/ssoProviders</code> resolves the SSO provider URL for the tenant. The user is redirected to the identity provider directly.</td>
    </tr>
    <tr>
      <td>Tenant selection</td>
      <td><code>/tenant</code></td>
      <td>Presented when no tenant is pre-selected in the query string. The tenant is appended to the redirect once chosen.</td>
    </tr>
    <tr>
      <td>MFA (TOTP)</td>
      <td><code>/mfa</code></td>
      <td>Triggered after password login when the user has MFA enrolled. A verification code is sent via <code>/services/sendVerificationCode</code> and validated before the final redirect.</td>
    </tr>
    <tr>
      <td>MFA enrolment redirect</td>
      <td>post-login</td>
      <td>When the account requires MFA but has not yet enrolled, the user is redirected to <code>setupMfaHost/setup-mfa</code> with the original OAuth parameters preserved.</td>
    </tr>
    <tr>
      <td>Forgot / Reset password</td>
      <td><code>/forgotPassword</code>, <code>/resetPassword</code></td>
      <td>Two-step flow: an email is dispatched via <code>/services/resetPassword</code>, then the user follows a tokenised link to set a new password.</td>
    </tr>
    <tr>
      <td>Zendesk SSO</td>
      <td><code>GET /</code> with <code>client_id=zendesk</code></td>
      <td>After successful login the server issues a Zendesk JWT and redirects to the Zendesk return URL.</td>
    </tr>
    <tr>
      <td>Token exchange</td>
      <td><code>/token</code>, <code>/services/token</code></td>
      <td>Standard OAuth token endpoint proxy; exchanges a login code for an access token.</td>
    </tr>
  </tbody>
</table>

## White-labelling

The app fetches tenant-specific theme configuration from `/services/theme` on startup. When a theme is present the MUI `ThemeProvider` is re-initialised with custom palette values and the Reltio favicon is hidden. This enables partners and customers to brand the login experience without a separate deployment.

## Security Hardening

- **Helmet** enforces HSTS (preload, 1-year max-age) and a strict Content Security Policy with per-request nonces for inline styles.
- **Redirect URL allowlist** — the `validateRedirectUrl` middleware rejects any `redirect_uri` not present in `redirectUrlList`.
- **State token** — an opaque state parameter is issued and validated across the OAuth round-trip to prevent CSRF.
- **CAPTCHA** — hCaptcha can be enabled per tenant to protect the login endpoint from credential-stuffing attacks.
- **JWT validation** — `jose` is used server-side to verify and decode tokens; raw token strings are never forwarded to the client.
