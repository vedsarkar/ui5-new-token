# Contributing to the Reltio Design Platform

This document is the **end-to-end guide** for working in the `reltio-design-platform` repository — from cloning the repo to getting a new release of `@reltio/design` into your consumer app. It is written for engineers inside and outside the UI Center of Excellence (CoE) team.

> **TL;DR**
> 1. Branch from `main`, commit your work in a feature PR.
> 2. Run `npm run changeset` — describe the user-visible impact, pick a bump type.
> 3. Open the PR. CI runs the tests, Chromatic, and a11y. Adding a changeset for source changes is convention today, not CI-enforced — a proper guard is on the backlog.
> 4. After merge, a CoE maintainer triggers `version @reltio packages` to cut a version PR. Reviewing and merging that PR is the only manual gate — the `release-packages` step then publishes automatically on the next `main` pipeline.

## Repository layout

`reltio-design-platform` is an npm-workspaces monorepo. The dev workspace (Storybook, design tokens, guides, scripts, tests) lives at the repository root. Publishable npm packages live under `packages/*`.

```
reltio-design/
├── .changeset/                  # release intents (one .md per PR)
├── .storybook/                  # Storybook configuration
├── .agents/skills/              # AI agent skills (Cursor, Claude Code, ...)
├── charts/                      # ECharts visualisations (source of @reltio/design/charts)
├── components/                  # Reltio MDM components + UI5 doc-only dirs
├── hooks/                       # Shared React hooks
├── utils/                       # Shared utilities (classNames, HtmlProps, ...)
├── guides/                      # MDX technical guides (live on reltio.design)
├── packages/
│   └── design/                  # @reltio/design — the only published package today
│       ├── package.json         # publish manifest, version
│       ├── components.ts        # re-export of /components
│       ├── charts.ts            # re-export of /charts
│       ├── hooks.ts             # re-export of /hooks
│       ├── utils.ts             # re-export of /utils
│       └── CHANGELOG.md         # generated by `changeset version`
├── public/                      # variables.css, fonts.css, static assets
├── scripts/                     # build & release tooling
└── bitbucket-pipelines.yml      # CI definitions
```

> **Adding a new publishable package.** Create `packages/<name>/` with its own `package.json` (must declare `"license": "Apache-2.0"`, `"publishConfig": { "access": "public" }`, must have a `dist/` build output and a `postbuild` step that copies the manifest, `README.md`, and the root `LICENSE` + `NOTICE` into `dist/`). Add the package name to your changesets where appropriate. The `release` pipeline picks it up automatically — no further changes to `scripts/release.mjs` or `bitbucket-pipelines.yml` are required.

## Prerequisites

| Tool | Version | Why |
|---|---|---|
| Node.js | `>=22` (see `.nvmrc`) | Toolchain target |
| npm | `>=10` (bundled with Node 22) | Workspaces support |
| Git | Recent | Standard |
| (Optional) Cursor or Claude Code | Latest | AI-assisted authoring uses skills in `.agents/skills/` |

We do not currently support pnpm or Yarn for this repository — npm workspaces are required because the `release` and `snapshot` scripts assume the npm lockfile and `--workspace=` flag.

## Getting started

```bash
git clone git@bitbucket.org:reltio-ondemand/reltio-design.git
cd reltio-design
nvm use            # picks Node 22 from .nvmrc
npm install        # installs all workspaces in one pass
npm run dev        # launches Storybook on http://localhost:6006
```

The first run will also build the design-tokens CSS, the component documentation, and the API report. After `npm run dev` is up, the **Reltio Design MCP** (`http://localhost:6006/mcp`) becomes available — Cursor and Claude Code attach to it on session start.

## Branching and pull requests

| Rule | Detail |
|---|---|
| **Branch from `main`** | Always. `main` is the only long-lived branch. |
| **One topic per branch** | Smaller PRs review faster and are safer to roll back. |
| **Title format** | `<type>: <imperative summary>` — `feat: add Chat composer`, `fix: align Avatar focus ring`, `docs: update token guide`. |
| **Description** | Link the Jira ticket, explain the _why_, list any breaking changes prominently. |
| **Squash-merge** | We squash on merge. The squash message becomes the commit on `main`. Keep it tidy. |
| **Required checks** | All checks in the `pull-requests` pipeline must be green: `test`, `chromatic`. |

> **About OpenSpec.** New Reltio business components and primitives go through the [spec-driven development workflow](https://reltio.design/?path=/docs/guides-spec-driven-development--docs) before code is written. Bug fixes, doc changes, and direct usage of UI5 components do not require a spec.

## Coding standards

All architectural rules live in [`AGENTS.md`](AGENTS.md). The most important ones:

- **UI5 first.** If `@reltio/design` already re-exports a UI5 component, use it. Wrap only when there is real MDM business value.
- **TypeScript `type` only**, no `interface`. Types live in separate `.types.ts` files.
- **CSS Modules + `classNames()`** for every Reltio component. Hardcoded hex colours are forbidden — use SAP Horizon `--sap*` tokens.
- **Plain CSS values** for typography, spacing, sizing, radii — no custom variables for those.
- **Biome** is the source of truth for formatting. `npm run format` before pushing.

Read [`AGENTS.md`](AGENTS.md) end to end if you have not seen it. AI agents in this repo are configured against the same rules, so following them keeps your PRs consistent with anything an agent produces.

## Storybook and tests

- Every Reltio component must have a `*.stories.tsx` file demonstrating each variant.
- Stories use the `autodocs` tag for automatic documentation.
- One story per variant; one story per free-form prop (don't create three stories for three values of the same string prop).
- Interaction tests live alongside stories (via `@storybook/addon-vitest`).
- Visual regression runs through Chromatic on every PR (`npm run deploy`).

Local commands:

```bash
npm run test        # vitest run
npm run coverage    # vitest with coverage report
npm run lint        # Biome check (no auto-fix)
npm run format      # Biome format with auto-fix
```

## Adding a changeset

Every PR that changes the source code of a published package **should** include a changeset. This is currently a convention rather than a CI-enforced gate — the previous guard only inspected `packages/*` and missed source changes that live under the root-level `components/`, `charts/`, `hooks/`, and `utils/` directories (they reach `@reltio/design` via the re-export layer in `packages/design/*.ts`). A new guard that traces those paths correctly is on the backlog. Until then, please add changesets by convention so the release notes stay accurate.

### What is a changeset?

A `.changeset/<random-name>.md` file declaring how this PR should affect package versions and CHANGELOG entries. The bump is **not** applied immediately — it is collected with all other pending changesets and applied in a single _Version Packages_ PR by a maintainer (see [Release process](#release-process)).

### How to add one

```bash
npm run changeset
```

The CLI walks you through three prompts:

1. **Which packages should bump?** — currently only `@reltio/design`; in the future, multi-package selection.
2. **What kind of bump?**

   | Bump | When to use |
   |---|---|
   | `patch` | Bug fix, perf fix, internal refactor, doc-only `*.tsx` change. No effect on the public API surface. |
   | `minor` | New component, new prop, new variant, additional types — anything **additive** that is safe to upgrade into. |
   | `major` | Renamed prop, removed export, behaviour change, restructured component API — anything a consumer would need to read a migration note for. |

3. **Summary** — what to write in `CHANGELOG.md`. Focus on **user-visible impact**.

After the prompts, a markdown file is created in `.changeset/`. Commit it as part of your PR.

### Writing a good summary

A good summary answers "what would a consumer's release notes say?" in 1–4 lines. Use full markdown — bullets, inline code, links — and write from the consumer's perspective.

```md
---
"@reltio/design": minor
---

Add streaming support to `Chat` component.

- New `messages` prop accepts an async iterator
- New `<Chat.Composer />` subcomponent for the input area
- Backwards-compatible with the existing static `messages` array shape
```

```md
---
"@reltio/design": major
---

Rename `Button` `kind` prop to `design` to align with UI5 naming.

**Migration:** rename every `<Button kind="…">` to `<Button design="…">`.
Codemod: `npx @reltio/codemods button-design-rename`.
See [the migration guide](https://reltio.design/?path=/docs/guides-migrations-button-design--docs).
```

### When _not_ to add a changeset

You don't need a changeset when your PR only touches:

- `*.story.mdx` documentation, guides, READMEs, comments
- `.storybook/`, `scripts/`, `biome.json`, `tsconfig.json` at the root
- `package.json` for dev dependencies that are not bundled

If you want to record an intentional "no version bump for this PR" (typically when versioning infrastructure or other changes that affect a published package only metadata-wise), use:

```bash
npm run changeset -- --empty
```

This creates a changeset with no frontmatter and is the convention for documenting "intentionally skipped".

### AI-assisted authoring

This repo ships an agent skill — [`.agents/skills/add-changeset/SKILL.md`](.agents/skills/add-changeset/SKILL.md) — that any AI assistant (Cursor, Claude Code, Copilot CLI, …) can use to write changesets for you. Trigger phrases:

- "Add a changeset for this PR"
- "What changeset should I write for these changes?"
- "Prepare release notes for this branch"

The skill inspects your diff, classifies the bump type, drafts the markdown, and writes the file. You still review and commit it.

## How releases happen

> **🎯 As a contributor, your only release-related task is the changeset.** Once your PR is merged, a CoE maintainer aggregates all pending changesets into a release.

The full mechanics — flow diagram, custom pipelines, semver policy, troubleshooting, and roles for maintainers and consumers — live in **[Guides → Release Process](https://reltio.design/?path=/docs/guides-release-process--docs)**. Read it once on onboarding; come back when you need to understand a specific edge case.

### What you need to know

1. **Merging a feature PR never publishes anything.** A maintainer first triggers `version @reltio packages` to cut a version PR. Only merging that version PR triggers a publish — and the publish itself is automated by the `branches: main` pipeline.
2. **Your changeset becomes a release-notes entry.** Whatever you write in the summary is what consumers will read in `CHANGELOG.md`.
3. **The release PR is reviewed.** Running `version @reltio packages` pushes a `release/version-*` branch and automatically opens the corresponding pull request into `main`. Anyone — including you — can comment on the proposed CHANGELOG entries before merge.

### Sharing your in-progress PR with a consumer

If a consumer app needs to test your PR before merge, ask a maintainer to run the **`snapshot @reltio packages`** custom pipeline against your branch. It publishes a one-off version under the dist-tag `pr-<id>` without touching `latest` or `CHANGELOG.md`.

```bash
# in the consumer app
npm install @reltio/design@pr-123
```

See [Guides → Release Process → Snapshot releases](https://reltio.design/?path=/docs/guides-release-process--docs#snapshot-releases) for the full lifecycle.

## Code review checklist

For reviewers — and a self-check before you request review:

### Code

- [ ] Endorsed UI5 component used where one exists; no needless wrapping
- [ ] Types in `.types.ts`, `type` keyword only
- [ ] `classNames()` used for every `className`
- [ ] Colours through `--sap*` tokens; plain values for everything else
- [ ] No component-level CSS variables unless properly encapsulated on the root element
- [ ] `npm run lint` and `npm run format` clean

### Storybook and tests

- [ ] One story per variant
- [ ] `autodocs` tag present
- [ ] Free-form props have a single demonstration story, not multiple
- [ ] Interaction tests cover the happy path and the most likely error state
- [ ] No visual regressions in Chromatic (or differences accepted with explanation)

### Release plumbing

- [ ] Changeset present, bump type matches the actual change
- [ ] Summary reads as a release note — written for consumers, not maintainers
- [ ] `major` changeset includes a migration note
- [ ] If touching a UI5 dependency version: explained in the PR description
