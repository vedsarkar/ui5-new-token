## Why

Today every `@reltio/auth` consumer is configured with a single static `oauthPath` (e.g. `https://auth.reltio.com/oauth`) and every `/checkToken` and `/refreshToken` call is forwarded to that one URL. The Reltio IDP team is moving the Auth Server from a single monolithic service into a **multi-environment architecture** (`auth.reltio.com`, `auth-idev-02.reltio.com`, `auth-test.reltio.com`, …), where access tokens are issued and validated by a specific cluster. The cluster that minted a token is the only cluster that can introspect or refresh it; pointing a `/checkToken` at the wrong cluster returns 401 even when the token is otherwise valid.

The cluster identity travels inside the access token as an `aurl` claim — a full URL (`https://auth-idev-02.reltio.com`). Every consumer BFF therefore has to **route per session** to the right cluster. The static `oauthPath` cannot do that.

A first attempt at this routing (decode `aurl` on every request, plus an `allowedAuthOrigins: string[]` allowlist in `AuthConfig` for SSRF protection) was rejected during review: the allowlist forces every new IDP cluster to fan out as a coordinated configuration change across ~20 consumer applications — `O(apps × clusters)` operator work owned by the UI Center of Excellence, repeated every time IDP adds a cluster. The whole point of dynamic routing is to keep cluster topology out of consumer apps.

This change ships routing inside `@reltio/auth` with **zero new consumer configuration**: the cluster URL is captured once at `/callback` time, sealed into an HMAC-signed `HttpOnly` cookie, and read back by every subsequent `/checkToken` and `/refreshToken` request. The HMAC key is derived from the existing `clientSecret` the package already requires, so no new operator step is introduced. Tampering with the cookie fails signature verification, and the router falls back fail-closed to the configured `oauthPath`.

## What Changes

- **New `reltio_aurl` cookie.** `HttpOnly`, `Secure` (when `secure: true`), `SameSite=Lax`, `Path=/`. Value format `base64url(aurl) + "." + base64url(mac)` where `mac` is the full 32-byte `HMAC-SHA-256(key, aurl)`. Same option vector as the existing `access_token` cookie.
- **HMAC key derivation.** A 32-byte routing key SHALL be derived as `SHA-256("reltio-auth-routing-v1:" + clientSecret)` from the single `deriveHmacKey` export in `src/core/signAurl.ts` (private). `createAuth(config)` — the single factory in the package — calls `deriveHmacKey` exactly **once** at construction time and captures the resulting `Promise<CryptoKey>` in the `AuthDeps` record (field `keyPromise`) it threads into every handler and OAuth/routing function. Both the mint side (handlers calling `signAurl(aurl, key)`) and the verify side (`resolveAuthPath`) read that one captured key — there is no second derivation. The label is fixed and versioned; it provides domain separation from any other use of `clientSecret` (HTTP Basic, future signing keys, etc.). Web Crypto is used for both derivation and HMAC; no Node-only APIs. The raw `CryptoKey` is reached only through `await options.keyPromise` inside the functions that sign or verify; it is never exposed on a public surface.
- **Internal `decodeAurl(token)` utility.** Reads the `aurl` claim from a Reltio JWT access token. Reltio access tokens use a non-standard envelope: `s.<base64url(payload)>.<base64url(signature)>` where the payload bytes are a 4-byte big-endian uint32 declared-length prefix followed by a zstd-compressed JSON claims object. Decompression uses the `fzstd` library (already pinned at `^0.1.1` on the existing `DESIGN-75` reference branch — same version reused here so the CoE does not re-evaluate the dependency). Four decompression-bomb guards, all anchored to a single `MAX_DECOMPRESSED_SIZE = 8 KiB` ceiling (encoded ceiling derived as `MAX_ENCODED_PAYLOAD_SIZE = ⌈(MAX_DECOMPRESSED_SIZE + 4) × 4 / 3⌉ ≈ 10 928 chars`, the base64url expansion of the largest legitimate payload), run in cheap-first order: (1) encoded-segment cap — early-exit when `segments[1].length` exceeds `MAX_ENCODED_PAYLOAD_SIZE` BEFORE `base64urlDecode` is called, closing the memory-amplification vector where an attacker sends a multi-megabyte segment of valid base64url characters that would otherwise allocate a proportional `Uint8Array` at decode time; (2) declared-size gate — early-exit when the 4-byte prefix exceeds 8 KiB, before any decompression allocation; (3) compressed-input cap — early-exit when the compressed bytes after the prefix exceed 8 KiB, closing the CPU-exhaustion vector where a lying small prefix is paired with a large compressed stream; (4) bounded output buffer — pass `new Uint8Array(declaredSize)` to `fzstd.decompress`, which throws `ZstdError` if the actual stream would write past the buffer, regardless of what the prefix said. Returns `string | null`; opaque UUID tokens, JWTs without an `aurl` claim, malformed envelopes, base64url failures, every guard trip, and any thrown error all return `null` — the function NEVER throws. Lives at `packages/auth/src/utils/decodeAurl.ts` and is NOT re-exported from `packages/auth/src/utils/index.ts` (internal by omission per the repo's barrel-pattern rule). The existing `DESIGN-75` branch already ships a working reference implementation at the same path — that implementation SHOULD be ported verbatim into `DESIGN-75-AURL` (it is mechanism-agnostic; the change in this proposal is only in WHERE the result is used, not in how `aurl` is decoded).
- **Internal `signAurl` / `verifyAurl` module.** Pure Web-Crypto HMAC sign and verify. `signAurl(aurl, key)` produces the cookie value via `crypto.subtle.sign`; `verifyAurl(cookieValue, key)` returns `string | null` (the verified `aurl`, or `null` on any parse/verify failure — never throws) via `crypto.subtle.verify`, which is constant-time by Web Crypto spec — no hand-rolled comparison. Lives at `packages/auth/src/core/signAurl.ts` (alongside `decodeAurl.ts` and `base64url.ts`) — private, since `core/` has no public subpath.
- **`GET /callback` mints the cookie.** After a successful authorization-code exchange, `decodeAurl(tokens.access_token)` runs once. When it returns a non-null string, the handler appends a third `Set-Cookie: reltio_aurl=<signed>` header. When it returns `null` (opaque UUID, JWT without `aurl`, malformed token, decompression-bomb guard tripped), no `reltio_aurl` cookie is set — subsequent requests fall back to `config.oauthPath`.
- **`POST /checkToken` routes via the signed cookie.** Routing is owned by the pure `resolveAuthPath(options)` function (options = `AuthDeps & { request }`). The handler forwards its flat `options` to `checkAccessToken({ ...options, accessToken, serviceId, tenantId })`, which calls `resolveAuthPath` internally; it reads the HMAC-signed `reltio_aurl` cookie and resolves to `${aurlOrigin}/oauth/checkToken` on success or `${oauthPathOrigin}/oauth/checkToken` on miss / verify failure, where `/oauth` is the hardcoded Reltio Auth Service base path (`OAUTH_BASE_PATH`) and the origin comes from the verified `aurl` claim or `config.oauthPath` respectively. The handler imports no cookie / HMAC / decode utilities — `decodeAurl` is NOT called on the incoming access token, closing the forged-JWT routing vector by construction.
- **`POST /refreshToken` routes via the signed cookie and re-mints after refresh.** Routing for the upstream `/token` call uses the same pure `resolveAuthPath` as `/checkToken` — the handler forwards `options` to `refreshAccessToken({ ...options, refreshToken })`. After a successful refresh, `decodeAurl` runs on the **new** access token: if non-null, `signAurl(aurl, await options.keyPromise)` mints a fresh `reltio_aurl` cookie; if `null`, the cookie is cleared with `Max-Age=0`. Atomicity rule mirrors `callbackHandler` — all three cookies are computed before any header is written, so any `signAurl` throw produces a 502 with no `Set-Cookie` headers. The cookie never points at a cluster the current token wasn't issued by.
- **`GET /logout` clears the cookie.** One additional `Set-Cookie: reltio_aurl=; Max-Age=0` header alongside the existing three. No upstream call, no HMAC verify, no `decodeAurl`.
- **New public resolver API — `resolveAuthPath` on the adapter return value.** `createExpressAuth(config)` and `createNextAuth(config)` expose `resolveAuthPath: (request: AnyRequest) => Promise<string>` — the **same** resolver the router uses internally, so the HMAC key is derived exactly once (alongside the router) and reused. It resolves the per-session Auth Server cluster URL from the signed `reltio_aurl` cookie, falling back to `config.oauthPath` on absence / parse-failure / verify-failure. Accepts Express `Request`, Next.js `NextRequest`, and Web `Request` uniformly through the existing `AnyRequest` adapter type — the same input surface used by `getAccessToken` / `getRefreshToken`. Chosen over a standalone factory in `@reltio/auth/utils` so that a single factory (`createAuth`) owns all once-derived state and the resolver cannot drift from the router's key or re-derive it; exposing it on the adapter return (not via `utils`) avoids pushing key-derivation and "build deps once" correctness onto consumers. Non-breaking: the Express adapter attaches the method to the returned `Router`; the Next.js adapter returns it alongside `handlers`. **Every consumer application that today calls an Auth Server API directly with a hardcoded `oauthPath`** — reading the token with `getAccessToken(req)` and POSTing to `${oauthPath}/...` to bypass the BFF — MUST replace hardcoded URLs with `${await auth.resolveAuthPath(req)}/...` (where `auth` is the value returned by `createExpressAuth` / `createNextAuth`) at every direct-call site so the direct call routes to the same cluster the BFF would have routed to. This applies fleet-wide to all 20+ `@reltio/auth` consumers; in a multi-cluster deployment a hardcoded `oauthPath` returns 401 for any user whose token was issued by a non-default cluster.
- **Routing fail-closed to `config.oauthPath`.** Every routing decision — cookie absent, malformed, wrong format, base64url decode failure, HMAC tag mismatch — falls back silently to `config.oauthPath`. The fallback path is the existing static-routing behaviour, so consumers without multi-cluster Auth Servers (most apps, today) keep working byte-for-byte unchanged.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `auth`: adds four new requirements (the `reltio_aurl` cookie, the HMAC key derivation, the dynamic OAuth cluster routing rule, and the `resolveAuthPath` resolver exposed on the adapter returns) and modifies six existing requirements (`GET /callback endpoint`, `POST /checkToken endpoint`, `POST /refreshToken endpoint`, `GET /logout endpoint`, `Cookie attributes`, `Framework-agnostic helpers`) to incorporate the new cookie and routing behaviour. No public `AuthConfig` field is added or removed. The `createExpressAuth(config)` and `createNextAuth(config)` return values gain an additive `resolveAuthPath` member (a method on the returned `Router` for Express, a field alongside `handlers` for Next.js) — no removed members, no mount-line edits required, non-breaking minor.

## Impact

- **Runtime code:**
  - `packages/auth/src/core/decodeAurl.ts` — new private module (in `core/`, no public subpath). Reads the `aurl` claim from a Reltio JWT with four decompression-bomb guards all anchored to a single `MAX_DECOMPRESSED_SIZE = 8 KiB` ceiling: encoded-segment cap (`segments[1].length > MAX_ENCODED_PAYLOAD_SIZE` → null, runs BEFORE base64url decode to bound the first allocation), declared-size gate (prefix > 8 KiB → null), compressed-input cap (compressed length > 8 KiB → null), bounded output buffer (`new Uint8Array(declaredSize)` — `fzstd.decompress` throws `ZstdError` on overrun, caught silently). Returns `string | null`; never throws. Port verbatim from the existing reference implementation on the `DESIGN-75` branch — the function is mechanism-agnostic.
  - `packages/auth/src/core/signAurl.ts` and `packages/auth/src/core/base64url.ts` — new private modules (in `core/`, no public subpath). `signAurl.ts` exports `deriveHmacKey(clientSecret): Promise<CryptoKey>`, `signAurl(aurl, key): Promise<string>`, `verifyAurl(cookieValue, key): Promise<string | null>`; `base64url.ts` is the shared codec they and `decodeAurl` use. All Web-Crypto, no Node imports.
  - `packages/auth/src/core/createAuth.ts` — the **single factory** in the package. At factory time it builds one `AuthDeps` record: `config`, `authHeader` (`Basic <getBasicToken(...)>`), and `keyPromise` (`deriveHmacKey(config.clientSecret)` — derived **once**). `config.clientSecret` is referenced exactly twice — once for the HTTP Basic credential, once for `deriveHmacKey` — and never on any per-request code path. Each request spreads the record into the handler's flat options (`route.handler({ ...deps, request })`); the exposed resolver does the same (`resolveAuthPath({ ...deps, request })`). The `AuthHandler` return type becomes `{ handle, resolveAuthPath }`.
  - `packages/auth/src/core/handlers/types.ts` — defines the flat `AuthDeps` record (`config`, `authHeader`, `keyPromise`) and `HandlerOptions = AuthDeps & { request }`; `Handler = (options: HandlerOptions) => Promise<Response>`. No bound `signAurl` on the context — handlers reach the key via `options.keyPromise`. The whole core uses the options-object pattern (one flat `options` argument per function).
  - `packages/auth/src/core/resolveAuthPath.ts` — new internal **pure function** `resolveAuthPath(options: AuthDeps & { request })`. Runs the `cookie → parseCookies → verifyAurl → (verified aurl ?? config.oauthPath) → origin + OAUTH_BASE_PATH` pipeline using `options.keyPromise`, where `OAUTH_BASE_PATH = "/oauth"` is the hardcoded Reltio Auth Service contract path. Used internally by the OAuth functions and exposed (bound to the factory's deps) on the adapter return values.
  - `packages/auth/src/core/handlers/callbackHandler.ts` — after `exchangeCode({ ...options, code })`, call `decodeAurl(tokens.access_token)`; when it returns a non-null string, `await signAurl(aurl, await options.keyPromise)` and prepare a third `Set-Cookie: reltio_aurl=<signedValue>` header. The `Set-Cookie` group is computed atomically *before* any header is written so a `signAurl` throw (extreme edge case) returns `502` with no `Set-Cookie` headers (`decodeAurl` is designed never to throw).
  - `packages/auth/src/core/handlers/checkTokenHandler.ts` — forward `checkAccessToken({ ...options, accessToken, serviceId, tenantId })`. Cookie reading and HMAC verification happen inside the pure `resolveAuthPath` that `checkAccessToken` calls, not in the handler. The handler never imports `verifyAurl` or `decodeAurl`, and never touches the `reltio_aurl` cookie directly — the forged-JWT routing vector closes here because routing is sourced exclusively from the signed cookie via `resolveAuthPath`.
  - `packages/auth/src/core/handlers/refreshTokenHandler.ts` — forward `refreshAccessToken({ ...options, refreshToken })`; routing for the upstream `/token` call is owned by `resolveAuthPath`. After a successful refresh, `decodeAurl(tokens.access_token)` runs on the **new** token. When it returns a non-null string, `signAurl(newAurl, await options.keyPromise)` mints a fresh `Set-Cookie: reltio_aurl=<signedValue>`. When it returns `null`, `clearCookie(AUTH_URL_COOKIE, ...)` clears the cookie. Atomicity rule matches `callbackHandler`.
  - `packages/auth/src/core/handlers/logoutHandler.ts` — one additional `Set-Cookie` appended via `clearCookie(AUTH_URL_COOKIE, cookieOptions)`. The handler never imports `decodeAurl`, `signAurl`, or `verifyAurl`.
  - `packages/auth/src/core/exchangeCode.ts`, `refreshAccessToken.ts`, `checkAccessToken.ts` — new internal **pure functions** (one export per file, replacing the former `createOAuthClient` factory object). Each takes a flat `options` (`AuthDeps & { …params }`). `exchangeCode` posts to `${config.loginPath}/token` (Login Page; unaffected by cluster routing). `refreshAccessToken` / `checkAccessToken` call `resolveAuthPath(options)` for the per-request upstream root, then dispatch to `${root}/token` / `${root}/checkToken`. The former `params` object on `checkToken` is flattened to `serviceId?` / `tenantId?` in the options.
  - `packages/auth/src/core/safeFetch.ts` — new internal helper (extracted from the former `createOAuthClient`). `safeFetch(options: RequestInit & { url })` applies the upstream-error policy (2xx → `Response`; 4xx → propagate; 5xx / network → `502 RequestError`). Shared by the three OAuth functions.
  - `packages/auth/src/utils/cookies.ts` — add a fourth constant `AUTH_URL_COOKIE = "reltio_aurl"` alongside the three existing constants.
  - `packages/auth/src/utils/index.ts` — no resolver export. The routing resolver is reached only through the adapter return values, not via `@reltio/auth/utils`.
  - `packages/auth/src/express/createExpressAuth.ts` — attaches `resolveAuthPath` to the returned `Router` (`Router & { resolveAuthPath }`); the `app.use(path, createExpressAuth(...))` usage is unchanged.
  - `packages/auth/src/next/createNextAuth.ts` — return shape becomes `{ handlers: { GET, POST }; resolveAuthPath }` (additive field next to `handlers`).

  - `packages/auth/src/types/index.ts` — no change. `AuthConfig` adds no field. `clientSecret` is reused as the HMAC key source.
