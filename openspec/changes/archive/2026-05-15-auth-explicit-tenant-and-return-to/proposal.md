## Why

The new `@reltio/auth` v1 still treats the `Referer` header as the only source of the tenant and the post-login return URL — exactly as the legacy `auth-middleware` did. The handlers extract the tenant via `refererUrl.searchParams.get("tenant")` and use `refererUrl.href` as the eventual `redirectUrl`. Consumers whose tenant lives in the URL **path** instead of the query string (HUB UI's `/hub/<tenant>/...` routing is the lead example) cannot use the package as-is and have to keep shipping their own `/login` and `/logout` routes that duplicate the package internals just to read the tenant from the right place. The HUB UI team confirmed during v1 review that the long-standing pain point is not resolved by the rewrite, and asked for either a more universal tenant lookup or a way to skip referer entirely.

## What Changes

- `GET /login` and `GET /logout` accept two new optional query parameters: **`?tenant=`** and **`?returnTo=`**. When either is present on the request, it takes precedence over the corresponding value derived from the `Referer` header.
- `Referer` becomes a **fallback** source, not a hard requirement. The handlers resolve `returnTo` and `tenant` from the request query first, then fall back to `refererUrl.href` and `refererUrl.searchParams.get("tenant")` respectively. If — and only if — both the `?returnTo=` query parameter and the `Referer` header are absent, the endpoints respond `400 Missing returnTo query parameter or Referer header`. Tenant remains optional: if neither source supplies one, the redirect simply omits the `tenant` parameter (the existing "no tenant" path).
- The OAuth callback URL (`redirect_uri` sent to the Login Page) is built from **client-supplied** components: the **origin** comes from the resolved return URL — `new URL(returnTo).origin` for the explicit path, `refererUrl.origin` for the referer fallback — and the **path** comes from `request.url.pathname.replace(/login$/, "callback")`. The BFF never derives the callback URL's origin from `request.url`, because the platform's reverse-proxy chain rewrites `Host`/`X-Forwarded-*` headers and the BFF effectively sees every incoming request on an internal origin. The path is still safe to read from `request.url` — reverse proxies preserve path segments because they route by them. This formalises what the existing code already does for the referer path and extends the same principle to the new explicit path.
- `?returnTo=` is validated for **shape and same-origin against `Referer` when both are present**: when an explicit `?returnTo=` is supplied alongside a `Referer` header, the handler asserts `new URL(returnTo).origin === refererUrl.origin` before forwarding to the Login Page; a mismatch produces `400 returnTo origin does not match Referer origin`. When `?returnTo=` is supplied alone (no `Referer`), the BFF cannot independently verify origin and forwards as-is — the Reltio OAuth server's `redirect_uri` allowlist remains the authoritative protection against open-redirect attacks in this path. The legacy referer-only path is unaffected.
- The `?tenant=` value must be a non-empty string; empty `?tenant=` is treated as absent and falls back to the referer source.
- The `Referer` URL parsing is allowed to fail soft when an explicit `?returnTo=` is present: a malformed `Referer` header is ignored (not 400) as long as the request's own query parameters cover both `tenant` and `returnTo` independently. A malformed `Referer` with no `?returnTo=` still responds `400 Malformed Referer header` as today.
- Storybook docs gain a new "Path-based tenant routing" section under the Setup and Migration guides, with HUB UI as the worked example showing the explicit `?tenant=` / `?returnTo=` usage from a Next.js middleware.
- This change is **non-breaking** for every existing consumer: when neither query parameter is supplied, the handler resolves both values from `Referer` exactly as today, including the existing `refererUrl.origin`-sourced callback URL host and the existing `validateRedirectUrl` check on `/callback`. The referer-only fallback path is byte-for-byte identical to v1.
- Defensive documentation is added to `packages/auth/src/express/adapter.ts` (`expressToWebRequest`), `packages/auth/src/next/createNextAuth.ts`, and `packages/auth/src/core/createAuth.ts` flagging that `Request.url`'s origin is unreliable behind the platform's reverse-proxy chain and is retained **only for backwards compatibility** with v1's `/callback` `validateRedirectUrl` and the public `ssoRedirect`-context shape. A planned follow-up proposal — `auth-trust-only-client-supplied-origins`, targeted for a future `@reltio/auth@2.0.0` — will remove the dependency entirely (cookie-schema rework on `/callback`, stable placeholder host in the Express adapter). The breaking change is explicitly accepted as the right long-term direction; this change just gets us to a state where new code never adds new dependencies on `request.url.origin`.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `auth`: the `GET /login endpoint` and `GET /logout endpoint` requirements are extended with the new query-parameter source resolution and eager `returnTo` validation. The `GET /callback endpoint` requirement is unchanged — the existing same-origin check on `redirectUrl` continues to apply.

## Impact

- **Runtime code:**
  - `packages/auth/src/core/handlers/loginHandler.ts` and `logoutHandler.ts` — rewrite the source-resolution logic; share a small helper (e.g. `resolveLoginContext`) to avoid drift between the two handlers.
  - `packages/auth/src/core/handlers/callbackHandler.ts` — no behavioural change; `?returnTo=` flows through the existing `redirectUrl` query parameter and the existing same-origin validation continues to enforce safety on the callback. A JSDoc warning is added at the call site flagging the `request.url`-origin dependency as scheduled for breaking removal.
  - `packages/auth/src/express/adapter.ts`, `packages/auth/src/next/createNextAuth.ts`, `packages/auth/src/core/createAuth.ts` — JSDoc updates only; no code change. Comments explicitly state that `Request.url.origin` is internal-only and retained for backwards compatibility.
- **Tests:** `packages/auth/tests/express/{login,logout}.test.ts` and the matching `tests/next/{login,logout}.test.ts` gain new scenarios covering explicit `?tenant=` / `?returnTo=`, the precedence rules, the cross-source check (`returnTo.origin === Referer.origin` when both are present), the resulting `redirect_uri` origin (from `returnTo` on the explicit path, from `Referer` on the fallback path), and the soft handling of a malformed `Referer` when query parameters are present. Existing referer-only scenarios stay green and lock the backwards-compatible behaviour.
- **Spec delta:** `openspec/specs/auth/spec.md` — modifies the two endpoint requirements; no new requirements added.
- **Storybook docs:** `guides/auth/Setup.Express.story.mdx`, `guides/auth/Setup.NextAppRouter.story.mdx`, `guides/auth/Migration.FromAuthMiddleware.story.mdx` — extended with the HUB-style worked example.
- **Consumers:** zero migration required. HUB UI (and any future path-based-tenant consumer) can drop its custom `/login` and `/logout` shim by switching the `<a href>` / fetch URL to include the explicit query parameters. `reltio-react-ui`, `admin-tools`, and the other twenty-something catalog apps continue to work unchanged.
- **Release vehicle:** minor `@reltio/auth` bump (additive, backwards-compatible). Changeset notes the new `?tenant=` / `?returnTo=` query parameters under "Added"; nothing under "Changed" — the referer-only legacy path is untouched and the new explicit path is an additive opt-in.
- **`@reltio/design` does not change.** This is a `@reltio/auth`-only release.
