## 2. `decodeAurl` — internal JWT payload reader with decompression-bomb guards

> A working reference implementation already exists at `packages/auth/src/utils/decodeAurl.ts` on the `DESIGN-75` branch (commits `0be33de feat(DESIGN-75): added compression guard` and earlier). That implementation is mechanism-agnostic — the `decodeAurl` contract (`(token: string) => string | null`) is identical whether routing is consumed via Proposal 1's `resolveAuthPath` or Proposal 2's signed cookie. The tasks below SHOULD be satisfied by porting the existing module verbatim and re-pinning `fzstd@^0.1.1` in `packages/auth/package.json`.

- [x] 2.1 Create `packages/auth/src/utils/decodeAurl.ts` exporting `decodeAurl(token: string): string | null`. The file SHALL NOT be re-exported from `packages/auth/src/utils/index.ts` — it is internal by omission per the repo's barrel-pattern rule, used only by `callbackHandler.ts` and `refreshTokenHandler.ts` (the resolver paths source routing from the signed cookie via `verifyAurl`, never from the JWT). The function SHALL recognise Reltio's non-standard access token envelope: `s.<base64url(payload)>.<base64url(signature)>` where the payload bytes are `[4-byte big-endian uint32 declared-length][zstd-compressed JSON claims]`. The function SHALL split the token on `"."`, require exactly three segments, require the first segment to equal the literal string `"s"`, base64url-decode the second segment to obtain the payload bytes, parse the 4-byte big-endian prefix as the declared decompressed-size, apply the four guards from task 2.2, decompress the remaining bytes via `fzstd.decompress(compressed, new Uint8Array(declaredSize))`, UTF-8-decode the result, `JSON.parse` it, and return `payload.aurl` when it is a non-empty string — otherwise `null`. The function SHALL return `null` for every error path and SHALL NEVER throw (a single top-level `try { ... } catch { return null; }` covers malformed envelopes, base64url failures, decompression errors including `ZstdError`, JSON parse failures, and unexpected payload shapes).
- [x] 2.2 Implement four decompression-bomb guards inside `decodeAurl`, all anchored to a single ceiling `const MAX_DECOMPRESSED_SIZE = 8_192;` (8 KiB — generous for real Reltio JWTs which decompress to ~500–1500 bytes, while still rejecting oversized inputs before any allocation). The encoded-side ceiling derives from the decompressed ceiling: `const MAX_ENCODED_PAYLOAD_SIZE = Math.ceil(((MAX_DECOMPRESSED_SIZE + 4) * 4) / 3);` (≈10 928 chars — base64url expansion of the largest legitimate payload plus the 4-byte length prefix):
  - **Guard 1 — encoded-segment cap.** Immediately after splitting the token on `"."` and validating the prefix, if `segments[1].length > MAX_ENCODED_PAYLOAD_SIZE`, `return null`. Runs BEFORE `base64urlDecode` so the actual first allocation site is bounded — without this gate, an attacker can send a multi-megabyte `segments[1]` of valid base64url characters that would force a proportional `Uint8Array` allocation inside `base64urlDecode` before any post-decode guard could fire (memory-amplification DoS vector). Zero-byte allocation on the reject path.
  - **Guard 2 — declared-size gate.** Immediately after parsing the 4-byte big-endian prefix, if `declaredSize === 0 || declaredSize > MAX_DECOMPRESSED_SIZE`, `return null`. Closes the "attacker claims a huge payload upfront" vector before any decompression memory is allocated.
  - **Guard 3 — compressed-input cap.** After taking `compressed = payloadBytes.subarray(4)`, if `compressed.length > MAX_DECOMPRESSED_SIZE`, `return null`. Closes the CPU-exhaustion vector where an attacker pairs a tiny lying prefix with a huge compressed stream so `fzstd` keeps parsing blocks until the bounded output fills. The bounded output buffer alone would not stop this — `fzstd` would still spend CPU on every block until the bound was reached.
  - **Guard 4 — bounded output buffer.** Pass `new Uint8Array(declaredSize)` as the second argument to `fzstd.decompress(compressed, out)`. `fzstd` throws `ZstdError` if the actual stream would write past `out.length`, regardless of what the 4-byte prefix said. The top-level try/catch returns `null` on the throw. Closes the lying-prefix + truthful-data vector (small declared size, real stream is much larger).
  Each guard SHALL carry an inline comment naming the attack class it defeats. Document all four above the function declaration in a JSDoc block.
  - **Implementation note:** Guard 1 (encoded-segment cap) was added in code review after the initial three-guard implementation shipped — CodeRabbit flagged that the existing guards ran *after* `base64urlDecode(segments[1])`, leaving the first allocation site unbounded. The fix added the pre-decode string-length check with a derived encoded ceiling. Regression test in `packages/auth/tests/utils/decodeAurl.test.ts` ("rejects a token whose encoded payload segment exceeds the encoded ceiling BEFORE base64url decoding") exercises a 50 000-char synthetic segment and asserts `null` is returned at the string-length check with zero byte allocations.
- [x] 2.3 Pin `fzstd@^0.1.1` as a runtime dependency under `dependencies` in `packages/auth/package.json`. The version SHALL match the version already in use on the `DESIGN-75` branch's `package.json`, so the CoE does not re-evaluate the dependency. The library was chosen for being a pure-JS minimal zstd decoder (~7 KB minified, no WASM, no Node-only imports) — characteristics required by the package's `Native fetch and Web Crypto` requirement that core files have no Node-only imports. Document the choice and size impact in a JSDoc comment at the top of `decodeAurl.ts`.
- [x] 2.4 Author `packages/auth/tests/utils/decodeAurl.test.ts` (Vitest, Node mode) and `packages/auth/tests/fixtures/aurlTokens.ts` (synthetic Reltio JWT fixtures, minted at fixture-author time via the `node:zlib` `zstdCompressSync` reference shown in the `DESIGN-75` branch's `aurlTokens.ts` header — the fixtures SHALL be committed as static strings, not minted at test time, so the test suite has no `node:zlib` dependency). ## 3. `signAurl` / `verifyAurl` — Web-Crypto HMAC module

- [x] 3.1 Create `packages/auth/src/utils/signAurl.ts` (placed alongside `decodeAurl.ts` from task 2.1, NOT re-exported from `utils/index.ts` — internal by omission) exporting three functions: `deriveHmacKey(clientSecret: string): Promise<CryptoKey>`, `signAurl(aurl: string, key: CryptoKey): Promise<string>`, `verifyAurl(cookieValue: string | undefined | null, key: CryptoKey): Promise<string | null>`. All Web-Crypto via `globalThis.crypto.subtle` — no `node:crypto`, no `node-forge`, no `jose`.
- [x] 3.2 `deriveHmacKey` SHALL:
  1. UTF-8 encode `"reltio-auth-routing-v1:" + clientSecret`.
  2. Compute `await crypto.subtle.digest("SHA-256", encoded)` → 32-byte `ArrayBuffer`.
  3. `await crypto.subtle.importKey("raw", digest, { name: "HMAC", hash: "SHA-256" }, false, ["sign", "verify"])` → `CryptoKey`.
  Return the `CryptoKey`. The `extractable: false` and the `usages: ["sign", "verify"]` SHALL match exactly. Document the `"reltio-auth-routing-v1:"` label as a versioned domain-separation tag with an inline comment.
- [x] 3.3 `signAurl` SHALL:
  1. UTF-8 encode the `aurl` string.
  2. Compute `await crypto.subtle.sign("HMAC", key, encoded)` → 32-byte `ArrayBuffer` (full HMAC-SHA-256 output).
  3. Return `base64url(encoded) + "." + base64url(mac)`. Base64url encoding SHALL be padding-free.
- [x] 3.4 `verifyAurl` SHALL:
  1. Treat `null`/`undefined`/empty-string input as a miss → return `null`.
  2. Split on `"."`. Require exactly two segments. Three+ segments → `null`. One segment → `null`.
  3. Base64url-decode both segments. Decode failure → `null`.
  4. Reject the cookie if the decoded MAC is not exactly 32 bytes (fast-fail length gate before reaching `crypto.subtle.verify`).
  5. Call `await crypto.subtle.verify("HMAC", key, receivedMac, aurlBytes)`; falsy result → `null`. Web Crypto's `verify` is constant-time by spec — no hand-rolled comparison.
  6. UTF-8 decode the first segment with `{ fatal: true }` to recover the `aurl` string. Decode failure → `null` (defence-in-depth — bytes that passed HMAC verify but are not valid UTF-8 cannot have come from `signAurl`).
- [x] 3.5 Helper: implement `base64urlEncode(buffer: ArrayBuffer | Uint8Array): string` and `base64urlDecode(value: string): Uint8Array | null` as small private functions in the same module. Padding-free, URL-safe alphabet (`A-Z`, `a-z`, `0-9`, `-`, `_`). Decode SHALL return `null` on any character outside the alphabet or any length not in `{4n, 4n+2, 4n+3}` after padding stripping.
- [x] 3.6 Author `packages/auth/tests/utils/signAurl.test.ts`. Scenarios: `deriveHmacKey` returns a `CryptoKey` with the documented algorithm and usages; same `clientSecret` produces the same key (verified by signing the same input twice and comparing); different `clientSecret` produces a different key (verified by sign→verify across two derived keys → `null`); `signAurl` then `verifyAurl` round-trips for ASCII `aurl`; round-trips for `aurl` with non-ASCII (e.g. encoded query strings — defensive, not expected in practice); tampered tag (flip one bit in the MAC segment) → `null`; tampered payload (flip one bit in the `aurl` segment) → `null`; truncated cookie (missing tag entirely) → `null`; extra dots in cookie → `null`; verifying with a different key → `null`; verifying empty/null/undefined input → `null`; verifying a base64url-invalid segment → `null`.
