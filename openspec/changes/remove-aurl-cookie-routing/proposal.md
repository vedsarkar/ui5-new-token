## Why

The BFF's per-session "which cluster issued this token?" routing ships as a dedicated HMAC-signed `reltio_aurl` cookie: `GET /callback` decodes the access token's `aurl` claim, signs it, and mints a third cookie; every later `POST /checkToken` and `POST /refreshToken` reads and verifies that cookie to pick the upstream cluster.

That mechanism cannot actually do multiauth, and carries real cost:

- **It assumes every cluster shares one `clientId` / `clientSecret`.** The cookie carries only the (signed) routing origin — never credentials — and the BFF authenticates every upstream `/checkToken` / `/token` call with a single, shared credential pair. But each `aurl` cluster is a distinct OAuth registration with its **own** `clientId` / `clientSecret`; routing a request's URL to a secondary cluster while still presenting the primary's credentials is rejected. Per-session routing has to select the cluster **and its credentials together**, which the cookie was never designed to carry.
- **A whole cryptographic subsystem exists only to protect the cookie.** `signAurl` / `verifyAurl` / `deriveHmacKey`, the `base64urlEncode` primitive, the `reltio-auth-routing-v1:` domain-separation label, the `keyPromise` threaded through `AuthDeps`, cookie mint/re-mint/clear plumbing across four handlers, and the writer/reader contract test — all of it exists solely to make the cookie tamper-proof.
- **An allowlist maps each cluster to its own credentials and needs no signing.** Keyed by the access token's `aurl`, each allowlist entry (the primary `oauthPath` plus every `authEnvironments` entry) carries that cluster's `clientId` / `clientSecret`, so a matched request is authenticated with the *right* credentials. It reaches the same SSRF-safety guarantee (a forged `aurl` can only ever *select* a pre-configured cluster, never introduce an arbitrary origin) with **no signing at all** — the routing input is the access token the request already carries.
- **The same allowlist model serves standalone API services with no cookie at all.** An introspection-only service needs the exact same "decode `aurl`, match the allowlist, use that cluster's credentials, fall back to the primary" resolution — it simply has no login flow to mint a cookie in the first place, so a cookie-based mechanism cannot serve it.

We unify on the allowlist everywhere: the BFF routes by the access token's `aurl` claim against the allowlist, the `reltio_aurl` cookie and its HMAC machinery are removed, and standalone API services introspect through the same factory (`auth.checkToken`, with an optional `loginPath`) rather than any separate token-checker factory or subpath. One mechanism, one factory.

## What Changes

- **Introduce a shared `AuthEnvironment` base type** (`{ oauthPath, clientId, clientSecret }`) and make `AuthConfig` extend it, then **add `authEnvironments: AuthEnvironment[]` to `AuthConfig`** as the allowlist of additional trusted environments. `POST /checkToken` and `POST /refreshToken` route to the cluster named by the access token's `aurl` claim, matched against the allowlist (the primary `oauthPath` + `authEnvironments`), with fail-open fallback to the primary cluster.
- **Rewrite `resolveAuthPath`** to resolve the request's cluster from the access token's `aurl` claim + allowlist, instead of verifying the `reltio_aurl` cookie. The public signature `(request) => Promise<string>` is unchanged.
- **Remove the `reltio_aurl` cookie entirely**: `GET /callback` and `POST /refreshToken` no longer mint/re-mint it; `GET /logout` no longer clears it; `POST /checkToken` no longer reads it. The BFF now sets exactly two auth cookies (`access_token`, `refresh_token`) plus the CSRF `state` cookie.
- **Delete the HMAC subsystem**: `signAurl`, `verifyAurl`, `deriveHmacKey`, the `AUTH_URL_COOKIE` constant, the `base64urlEncode` primitive, and the `keyPromise` field on `AuthDeps`. `AuthDeps` now carries the precomputed allowlist instead.
- **No standalone token-checker surface.** `@reltio/auth` exposes no `createTokenChecker` factory, no `@reltio/auth/api` subpath, and no `TokenCheckerConfig` type. Standalone API services introspect via `createExpressAuth(config).checkToken` / `createNextAuth(config).checkToken` — the same allowlist-based introspection, no second factory.
- **Make `loginPath` optional in `AuthConfig`.** It is only needed for the interactive OAuth flow (`GET /login`, `GET /logout`, `GET /callback`); an introspection-only API service configures without it. Those three routes respond `500` when `loginPath` is absent; `checkToken` / `resolveAuthPath` remain fully functional.
- **Net-additive (`minor`) for published consumers.** The public adapter API (`createExpressAuth`/`createNextAuth` return shape, `resolveAuthPath`, `checkToken`) is unchanged in signature; only the routing mechanism behind it changes, and single-cluster deployments keep working with no config change. Multiauth BFF deployments configure the new optional `authEnvironments` to route to non-primary clusters. The `reltio_aurl` cookie was `HttpOnly` and never public API — its removal is transparent to published consumers. (No `createTokenChecker` / `@reltio/auth/api` surface ever shipped, so there is nothing for a consumer to migrate off of.)

## Capabilities

### Modified Capabilities

- `auth`: Per-session cluster routing moves from the HMAC-signed `reltio_aurl` cookie to the access token's `aurl` claim matched against an `AuthConfig.authEnvironments` allowlist (each entry sharing the new `AuthEnvironment` base type). The `reltio_aurl` cookie, HMAC key derivation, and the sign/verify primitives are removed. Standalone API-service introspection is served by the existing `auth.checkToken` (no separate `createTokenChecker` factory / `@reltio/auth/api` subpath / `TokenCheckerConfig` type), and `loginPath` becomes optional so one factory serves both BFFs and standalone API services. `GET /callback`, `POST /refreshToken`, `POST /checkToken`, `GET /logout`, the cookie-attributes contract, `resolveAuthPath`, the framework-agnostic-helpers narrative, and the configuration shape are all updated accordingly.

## Impact

- `packages/auth/src/types/index.ts`: a shared `AuthEnvironment` base type is added; `AuthConfig` extends it and gains optional `authEnvironments: AuthEnvironment[]`; `loginPath` becomes optional; no `TokenCheckerConfig` type is added.
- `packages/auth/src/core/`: `aurlCookie.ts` deleted; `allowlist.ts` (`buildAllowlist`, `selectAuthService`, `selectAuthServiceForRequest`) and `checkAccessToken.ts` are the shared routing/introspection core for every path; `resolveAuthPath.ts`, `refreshAccessToken.ts`, `exchangeCode.ts`, `createAuth.ts`, and the four handlers route via the allowlist; the three login-flow handlers guard on a missing `loginPath` (respond `500`); `AuthDeps` drops `keyPromise`/`authHeader` and carries `allowlist`.
- `packages/auth/src/utils/cookies.ts`: `AUTH_URL_COOKIE` removed. `packages/auth/src/core/base64url.ts`: `base64urlEncode` removed.
- Tests updated across the package: cookie-minting helpers and `reltio_aurl` scenarios replaced with `aurl`-claim + allowlist routing scenarios; introspection-only (no `loginPath`) coverage added.
- Docs updated: `packages/auth/README.md`, the Dynamic OAuth Routing guide, and `packages/auth/AGENTS.md`.
- Consumers: multiauth BFF deployments configure `authEnvironments`; single-cluster deployments are unaffected (every request resolves to `oauthPath`). No consumer interacts with `reltio_aurl` directly, so its removal is transparent to correct integrations.
