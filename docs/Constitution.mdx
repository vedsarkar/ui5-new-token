# Reltio Design Constitution

## Core Principles (NON-NEGOTIABLE)

### I. Component-First Architecture
All functionality MUST be delivered as self-contained, reusable React components. Components MUST be independently testable, documented, and exportable. Each component MUST have a clear, single responsibility. Components MUST be organized in their own directories with associated styles, stories, and tests. No component should depend on application-specific logic or context.

### II. TypeScript Strict Mode 
All code MUST be written in TypeScript with strict mode enabled. Type safety is mandatory - no `any` types without explicit justification. All component props MUST be fully typed. Public APIs MUST export TypeScript types. Type definitions MUST be kept in sync with implementation.

### III. Storybook Documentation
Every component MUST have a corresponding Storybook story file. Stories MUST demonstrate all component variants, states, and use cases. Stories serve as both documentation and visual regression testing. All interactive examples MUST be functional and representative of real-world usage. Each story MUST contain only one variant of the component. Stories that display multiple variants, states, or combinations (such as "All Variants", "All States", "All Sizes", "VariantsAndSizes", etc.) MUST NOT be created. Each component variant, state, size, or combination MUST have its own separate story. Rationale: Individual stories provide better isolation for testing, clearer documentation, and more precise visual regression testing.

### IV. CSS Modules for Styling
Component styles MUST use CSS Modules for scoped styling. Each component MUST have its own `.module.css` file. Global styles MUST be avoided unless explicitly justified. CSS Modules provide automatic scoping and prevent style conflicts across components.

### V. Code Quality Standards
All code MUST pass Biome linting and formatting checks before commit. Code formatting MUST follow Biome configuration (tabs for indentation, double quotes for strings). Unused imports, variables, and parameters MUST be removed. Code reviews MUST verify linting compliance.

### VI. Versioning & Breaking Changes
Versioning MUST follow semantic versioning (MAJOR.MINOR.PATCH). Breaking changes to component APIs, prop interfaces, or public exports require MAJOR version bump. New features without breaking changes require MINOR version bump. Bug fixes and non-breaking improvements require PATCH version bump. All breaking changes MUST be documented in changelog with migration guide.

### VII. English Language Requirement
All files in the repository MUST use English language exclusively. This includes but is not limited to: source code, comments, documentation, commit messages, pull request descriptions, configuration files, and all written content. Code comments, function names, variable names, documentation strings, README files, and any other text content MUST be written in English. This ensures consistency, maintainability, and accessibility for all team members and contributors regardless of their native language.

### VIII. classNames Utility Requirement
All component elements MUST use the `classNames` utility from `utils/classNames.ts` for combining CSS class names. Direct string concatenation, template literals, or manual class name joining MUST NOT be used. This function provides stable, predictable class names without CSS Modules hash suffixes, enabling external developers to easily customize styles of internal component elements using stable selectors. All `className` attributes in components MUST use `classNames()` function calls.

### IX. CSS Custom Properties Requirement
All components MUST define ALL unique CSS custom properties (CSS variables) on the root element (`.root` class). All internal elements and CSS selectors within the component MUST use ONLY these CSS variables - direct color values, spacing values, or other design tokens MUST NOT be used directly. CSS variables MUST start with the prefix `--reltio-{component-name}-` (e.g., `--reltio-button-`). The remainder of the variable name can use any descriptive naming (e.g., `--reltio-button-height`, `--reltio-button-on-focus-bg`, `--reltio-button-color-primary`).

### X. TypeScript Type Requirement
All TypeScript type definitions MUST use `type` keyword instead of `interface`. This applies to all type definitions including component props, function parameters, return types, and any other type declarations. The `interface` keyword MUST NOT be used. This ensures consistency across the codebase and provides better flexibility for type composition, intersection types, and union types. Rationale: `type` provides more flexibility for advanced TypeScript patterns (union types, mapped types, conditional types) and maintains consistency with modern TypeScript best practices.

### XI. Component Types File Structure
All TypeScript type definitions for a component MUST be defined in a separate `.types.ts` file (e.g., `Button.types.ts` for the Button component). This file MUST be located in the same directory as the component implementation file. All component-related types (props, variants, sizes, and any other exported types) MUST be defined in this file. The component implementation file MUST import types from the `.types.ts` file. This ensures clear separation of concerns, improves maintainability, and follows the same pattern as `.module.css` and `.stories.tsx` files. Rationale: Separating types into their own file improves code organization, makes types easier to find and maintain, and provides a consistent file structure across all components.
